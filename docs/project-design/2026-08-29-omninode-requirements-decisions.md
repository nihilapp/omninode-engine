# 옴니노드 요구사항 결정 기록

> 분류: 프로젝트 설계
>
> 목적: 마스터와의 설계 대화에서 확정된 선택을 즉시 보존한다.
>
> 기록 원칙: `확정`은 마스터가 명시적으로 선택한 항목만, `미결`은 아직 답변을 받지 못한 항목만 기록한다. 이 문서는 구현 지시나 데이터베이스 명세가 아니다.

## 문서 정보

- 생성일: 2026-08-29
- 상태: 진행 중

## 확정 결정

### 공통 식별자

1. 사용자 정의 카테고리·템플릿·관계 유형·템플릿 섹션의 내부 코드는 시스템이 자동으로 생성한다.
2. 관리자는 사람이 읽는 이름만 입력하며, 내부 코드는 관리 화면에 표시하거나 입력·수정하는 대상이 아니다.
3. 내부 코드는 참조와 프로그램 운영의 기반이므로 생성 후 누구도 변경할 수 없다.
4. 새 월드와 프로젝트를 만들면 기본 제공 관계 유형·카테고리·템플릿은 모두 활성화된 상태로 시작한다. 관리자가 필요 없는 항목을 비활성화한다.
5. 옴니노드의 모든 데이터 삭제는 소프트 딜리트로 처리한다. 삭제된 데이터는 보존하며, 권한 있는 관리자가 복구할 수 있어야 한다.
6. 삭제된 데이터는 통합 휴지통이나 별도 삭제 목록으로 구분하지 않는다. 문서·카테고리·템플릿·관계 등 각 관리 화면의 일반 항목 목록에 함께 표시하고, 상태 필터로 삭제 항목을 포함하거나 따로 볼 수 있게 한다.
7. 월드 또는 프로젝트를 삭제하면 해당 월드·프로젝트만 삭제 상태로 둔다. 하위 프로젝트·문서·카테고리·템플릿 등의 자체 삭제 상태는 바꾸지 않지만, 삭제된 상위 항목에 속한 동안에는 함께 접근할 수 없다. 월드 또는 프로젝트를 복구하면 하위 데이터는 삭제 전 상태로 다시 접근할 수 있다.
8. 계정 기능은 일반 데이터 삭제와 구분하여 `탈퇴`로 표현한다. 탈퇴를 요청하면 즉시 로그아웃하고 일반 서비스 접근을 막는다.
9. 탈퇴를 요청한 계정은 일반 서비스에 다시 접근하거나 계정을 복구할 수 없다. 다만 탈퇴 요청 시점부터 7일 동안은 자신이 만든 데이터를 내려받을 수 있다.
10. 7일이 지나면 계정과, 부관리자가 없는 소유 월드 및 하위 프로젝트·문서·카테고리·템플릿·관계·태그 등 모든 데이터를 서비스 DB에서 완전 삭제한다. 이 데이터는 소프트 딜리트 대상이 아니다.
11. 서비스 운영을 위한 내부 백업은 장애 대응 목적의 별도 운영 정책으로 둔다. 이는 탈퇴 계정이 데이터를 복구하거나 내려받는 기능을 뜻하지 않는다.
12. 새 항목을 만들 때 같은 범위에 같은 이름의 삭제된 항목이 있으면, 해당 항목을 복구할지 새로 만들지 안내한다. 복구를 선택하면 그 항목과 연관 데이터를 함께 복구하고, 새로 만들기를 선택하면 기존 삭제 항목과 별개의 새 항목을 만든다.
13. 탈퇴 데이터 내려받기에는 탈퇴 계정이 소유한 월드의 전체 데이터와, 다른 월드에서 그 계정이 작성한 문서·관계만 포함한다. 다른 관리자가 소유한 공동 관리 월드의 전체 데이터는 포함하지 않는다.
14. 탈퇴 데이터는 하나의 ZIP 파일로 제공한다. ZIP에는 사람이 읽을 수 있는 문서별 Markdown 파일과 카테고리·태그·관계 등 구조 보존용 JSON 파일을 함께 담는다.
15. 탈퇴 계정이 다른 관리자의 월드에서 작성한 문서·관계는 7일 뒤에도 해당 월드 데이터로 유지한다. 탈퇴 계정의 로그인 정보·권한·소속만 제거하며, 작성자 표시가 필요한 경우에는 `탈퇴한 관리자`로 표시한다.
16. 탈퇴 요청 뒤에는 일반 로그인과 서비스 기능을 모두 차단한다. 7일 동안의 데이터 내려받기는 탈퇴 안내 이메일의 전용 링크로만 허용하며, 만료 전에는 같은 링크를 반복 사용할 수 있다.
17. 탈퇴 데이터 내려받기 전용 링크는 7일 안에 같은 이메일로 재발송할 수 있다. 재발송하면 이전 링크는 즉시 무효화하고 새 링크만 유효하게 한다.
18. 탈퇴 계정이 소유한 월드에 부관리자가 있으면, 탈퇴 요청을 확정하는 즉시 탈퇴자가 지정한 부관리자 한 명을 관리자로 승격하고 월드 소유권을 넘긴다. 이 월드와 하위 데이터는 삭제하지 않는다. 부관리자가 없는 소유 월드만 완전 삭제한다.
19. 소유권을 승계받아 관리자가 된 계정은 해당 월드의 관리자 전체 허가를 받는다. 기존 부관리자 범위의 개별 허가는 더 이상 적용하지 않는다.
20. 탈퇴 데이터 내려받기 결과는 탈퇴 확정 시점의 대상 데이터 스냅샷으로 만든다. 이후 다른 관리자가 해당 데이터를 수정하거나 삭제해도 7일 내려받기 기간의 결과는 바뀌지 않는다.

### 월드와 프로젝트

1. 월드 이름은 서비스 전체에서 일괄 중복 검사하지 않는다. 같은 관리자가 만든 월드끼리만 이름 중복을 허용하지 않는다.
2. 프로젝트 이름은 같은 월드 안에서 중복을 허용하지 않는다. 서로 다른 월드의 프로젝트 이름은 중복될 수 있다.

### 관계 유형과 관계 인스턴스

1. 옴니노드는 범용 기본 관계 유형 936개를 첫 버전부터 모두 제공한다.
2. 기본 관계 유형의 활성화와 비활성화는 프로젝트가 아니라 **월드 단위**로 관리한다.
3. 시스템 기본 관계 유형은 수정·삭제할 수 없다. 월드에서는 활성화·비활성화만 할 수 있고, 특수한 관계는 월드 사용자 정의 관계 유형으로 추가한다.
4. 관리자는 자신의 월드에서 기본 관계 유형 외의 사용자 정의 관계 유형을 추가할 수 있다.
5. 관계 인스턴스는 문서 대상 2개 이상, 최대 4개로 구성한다.
6. 관계 유형은 참여자 역할과 역할별 허용 문서 카테고리를 반드시 정의한다.
7. 관계 생성 화면과 서버 검증은 허용되지 않은 카테고리의 문서 선택을 막아야 한다.
8. 관계 유형마다 각 참여자 역할의 반복 가능 여부를 설정한다.
9. 관계는 한 번만 저장한다. 같은 관계는 보는 문서의 위치에 따라 정방향 또는 역방향 표현으로 표시한다.
10. 관계의 시작·종료 시점은 선택 입력이다. 비워 두어도 관계를 만들 수 있으며, 창작물 안의 시간 표기가 다양하므로 날짜·시간 형식으로 제한하지 않는 문자열로 기록한다.
11. 관계 상세 페이지에는 선택적인 설명과 관련 설정 문서 링크를 함께 표시한다. 이를 위한 별도 근거 문서나 독립 기록 화면은 만들지 않는다.
12. 관계 설명은 기본 서식과 위키링크를 지원한다.
13. 관계 수정·삭제에는 누가 언제 무엇을 바꿨는지 확인할 수 있는 단순 변경 이력을 남긴다. 관계 리비전의 복원 기능은 제공하지 않는다.
14. 관계 유형을 비활성화하면 새 관계 생성은 물론 그 유형으로 이미 만들어진 모든 관계도 즉시 끊는다. 비활성화된 유형의 관계는 문서 관계 목록과 관계도에 표시하거나 수정할 수 없다.
15. 사용 중인 사용자 정의 관계 유형은 삭제할 수 없고 비활성화만 허용한다. 더 이상 관계에서 참조되지 않을 때만 삭제할 수 있다.
16. 공개 문서의 관계 목록과 관계도에서 비공개 문서는 ‘비공개 문서’로 표시한다. 뷰어가 클릭하면 접근 권한 없음으로 처리한다.
17. 같은 관계 유형에서 참여 문서와 각 문서의 참여자 역할 구성이 모두 같으면 중복 관계로 보고 새로 만들 수 없게 한다.
18. 비활성화한 관계 유형을 다시 활성화해도, 비활성화할 때 끊긴 기존 관계는 복원하지 않는다. 필요한 관계는 새 관계로 다시 만들어 쌓는다.
19. 한 번이라도 관계에 사용한 사용자 정의 관계 유형은 참여자 역할과 역할별 허용 카테고리 같은 구조를 변경할 수 없다. 다른 구조가 필요하면 새 관계 유형을 만든다.
20. 관계 유형 비활성화로 끊긴 관계 인스턴스는 소프트 딜리트로 기록만 보존하고, 관계 관리 화면의 상태 필터에서 확인할 수 있다. 이 관계는 복구할 수 없으며, 관계 유형을 다시 활성화한 뒤에도 필요한 관계는 새로 만들어야 한다.

### 카테고리

1. 문서는 최대 3단계 카테고리 중 필요한 깊이까지만 선택할 수 있다. 하위 카테고리가 존재해도 가장 아래 단계 선택을 강제하지 않는다.
2. 템플릿은 대분류 카테고리에 연결한다.
3. 템플릿이 연결된 대분류 카테고리에서 만드는 문서는 반드시 그 템플릿을 적용해야 한다. 같은 카테고리 안에서 서로 다른 템플릿을 적용한 문서는 허용하지 않는다.
4. 카테고리는 템플릿을 할당하지 않을 수 있다.
5. 템플릿이 연결되지 않은 대분류 카테고리에서는 문서를 만들 수 없다. 문서 생성 전 해당 카테고리에 템플릿을 먼저 연결해야 한다.
6. 하나의 템플릿은 여러 카테고리에 동시에 할당할 수 있다.
7. 서로 다른 템플릿이 연결된 대분류 카테고리 사이의 문서 이동은 허용한다. 이동 시 대상 템플릿을 적용하고, 기존 섹션마다 문서의 추가 섹션으로 남기거나 삭제할지를 관리자가 직접 선택한다.
8. 대분류 카테고리에 템플릿을 연결하거나 해제하는 작업은 카테고리 관리 페이지에서 수행하며, 카테고리 관리 허가만 필요하다.
9. 서로 다른 템플릿 카테고리로 문서를 이동할 때 기존 섹션을 자동으로 삭제하지 않는다.
10. 같은 템플릿을 공유하는 대분류 카테고리 사이에서는 문서 이동을 허용한다.
11. 문서가 있거나 하위 카테고리가 남아 있는 카테고리는 삭제할 수 없다. 삭제 전 문서를 다른 카테고리로 이동하고 하위 카테고리를 정리해야 한다.
12. 시스템 기본 카테고리는 수정·삭제할 수 없다. 프로젝트에서는 활성화·비활성화만 할 수 있고, 특수한 분류는 프로젝트 사용자 정의 카테고리로 추가한다.
13. 사용 중인 카테고리를 비활성화하면 새 문서 작성과 카테고리 변경에서 선택할 수 없게 한다. 기존 문서의 분류와 표시는 유지한다.
14. 같은 부모 카테고리 아래에서는 카테고리 이름을 중복할 수 없다.
15. 같은 부모 카테고리 안의 표시 순서는 관리자가 위·아래 이동 버튼으로 조정한다. 드래그 방식은 사용하지 않는다.
16. 카테고리는 다른 상위 카테고리 아래로 옮길 수 있다. 이때 영향받는 문서·템플릿·관계 구조는 모두 점검 대상으로 전환한다.
17. 카테고리 이동으로 점검 대상이 된 항목이 공개 상태라면 즉시 비공개로 전환한다. 점검이 끝나기 전에는 다시 공개할 수 없다.
18. 카테고리 이동으로 발생한 점검은 시스템 자동 판정으로 끝내지 않는다. 관리자가 영향 항목을 직접 확인한 뒤 완료 처리해야 다시 공개할 수 있다.
19. 프로젝트 사용자 정의 카테고리는 대분류로 만들거나 시스템 기본 카테고리 아래의 하위 카테고리로 만들 수 있다. 같은 프로젝트의 사용자 정의 카테고리 아래에도 둘 수 있다.

### 템플릿

1. 템플릿의 첫 섹션인 ‘개요’만 필수 섹션으로 둔다. 그 밖의 템플릿 섹션은 모두 선택 섹션이다.
2. 필수 섹션은 문서에서 위치를 변경할 수 없다.
3. 새 선택 섹션은 ‘개요’ 아래의 어느 위치에나 추가할 수 있으며, 기존 선택 섹션 사이에도 둘 수 있다.
4. 문서에는 템플릿 외의 추가 섹션을 만들 수 있다. 추가 섹션은 필수 섹션 사이 또는 맨 끝에 둘 수 있다.
5. 추가 섹션은 기준 필수 섹션과 같은 헤딩 레벨이거나 더 하위 헤딩 레벨이어야 한다.
6. 템플릿의 첫 필수 섹션은 항상 ‘개요’이며, 그 위에는 추가 섹션을 둘 수 없다.
7. 템플릿 섹션 데이터는 참조 가능한 코드로 관리한다. 문서는 이 코드 참조로 섹션의 순서와 라벨을 기록해 언제 불러와도 같은 구조로 복원한다.
8. 문서의 필수 섹션 본문은 템플릿 섹션의 변경되지 않는 내부 식별값에 연결한다.
9. 템플릿 섹션 코드는 문서 참조와 프로그램 운영의 기반이므로, 문서 사용 여부와 관계없이 운영자를 포함한 누구도 변경할 수 없다.
10. 템플릿의 필수 섹션 제목, 헤딩 레벨, 순서가 바뀌면 해당 템플릿을 사용하는 현재 문서는 최신 템플릿 구조에 따라 렌더링한다.
11. 템플릿에서 섹션 이름만 바뀌어도 내부 식별값이 유지되면 기존 본문은 같은 섹션의 내용으로 보존한다.
12. 필수·선택 여부와 문서 사용 여부에 관계없이 모든 템플릿 섹션은 삭제할 수 없다.
13. 특정 템플릿 섹션이 필요 없는 문서 구조는 해당 섹션이 없는 별도 템플릿을 새로 만들어 사용한다. 이는 기존 구조를 변경하거나 제거하기보다 새 구조를 명시적으로 만드는 옴니노드의 기본 기조다.
14. 템플릿 리비전은 템플릿 최초 생성 시 한 번 만들고, 이후 실제 수정이 저장될 때마다 새로 만든다.
15. 과거 템플릿 리비전으로 되돌리는 동작만으로는 새 템플릿 리비전을 만들지 않는다.
16. 새 템플릿 리비전은 자신이 기반으로 삼은 이전 템플릿 리비전 ID를 함께 저장해 리비전 계보를 추적할 수 있어야 한다.
17. 시스템 기본 템플릿은 수정·삭제할 수 없다. 프로젝트에서는 활성화·비활성화만 할 수 있고, 필요한 변형은 프로젝트 사용자 정의 템플릿으로 만든다.
18. 사용 중인 템플릿을 비활성화하면 새 문서 생성과 새 카테고리 연결만 막는다. 기존 문서와 과거 리비전은 기존 템플릿 리비전으로 계속 렌더링한다.
19. 사용 중인 사용자 정의 템플릿은 삭제할 수 없고 비활성화만 허용한다. 더 이상 문서나 카테고리에서 참조되지 않을 때만 삭제할 수 있다.
20. 같은 프로젝트 안에서는 템플릿 이름을 중복할 수 없다.
21. 필수 템플릿 섹션은 작성 중 저장에서는 비워 둘 수 있지만, 문서를 공개 반영할 때는 모든 필수 섹션의 본문이 채워져 있어야 한다.
22. 같은 템플릿 안에서는 섹션 이름을 중복할 수 없다.
23. 템플릿의 선택 섹션 순서는 드래그가 아니라 위·아래 이동 버튼으로 조정한다.
24. 기존 문서가 사용하는 템플릿에 선택 섹션을 새로 추가해도, 해당 문서를 수정·저장해 새 문서 리비전이 생기기 전에는 문서 섹션과 새 템플릿 섹션을 연결하지 않는다. 따라서 수정 전 읽기 화면에는 새 선택 섹션이 보이지 않는다.
25. 기존 문서를 수정·저장해 새 문서 리비전을 만들면 그 시점의 최신 템플릿 구조를 적용한다. 선택 섹션을 문서에 적용하기 위한 별도 동작은 두지 않는다.
26. `템플릿 점검 필요`는 문서의 최신 문서 리비전이 참조하는 템플릿 리비전과 현재 적용 중인 템플릿 리비전이 다른 상태를 뜻한다. 템플릿 수정으로 새 템플릿 리비전이 생기거나 과거 템플릿 리비전으로 되돌아가 현재 적용 리비전이 바뀌면, 해당 템플릿을 사용하는 문서의 이 상태를 다시 계산해 문서 관리 목록에 표시한다. 이 표시는 기존 문서를 자동 변경하거나 공개 상태를 바꾸지 않으며, 관리자가 최신 템플릿 구조 적용 여부를 확인하기 위한 운영 표시다.
27. `템플릿 점검 필요` 상태의 문서를 수정 페이지에서 저장해 현재 적용 중인 템플릿 리비전을 새 문서 리비전에 연결하면, 해당 문서의 `템플릿 점검 필요` 상태를 자동으로 해제한다. 별도의 점검 완료 동작은 두지 않는다.

### 문서와 문서 리비전

1. 문서는 마크다운 본문 전체가 아니라 섹션별 본문을 저장한다.
2. 문서 리비전은 본문뿐 아니라 카테고리, 태그, 이름, 세계관 안에서의 시작·종료 시점, 연결 템플릿 등 해당 시점의 문서와 연관된 상태를 함께 보존한다. 공개 여부와 공개할 리비전 선택은 문서의 현재 공개 상태로 별도 관리한다.
3. 문서 리비전은 해당 시점의 템플릿 리비전을 반드시 함께 참조하도록 연결한다.
4. 현재 문서는 최신 템플릿 구조로 렌더링하고, 과거 문서 리비전은 저장 당시 연결된 템플릿 리비전 구조로 렌더링한다.
5. 문서 본문, 카테고리, 연결 템플릿, 태그, 이름, 세계관 안에서의 시작·종료 시점 등 문서와 관련된 상태를 저장할 때마다 새 문서 리비전을 만든다. 공개 반영과 비공개 전환만으로는 새 문서 리비전을 만들지 않는다.
6. 새 문서 리비전은 자신이 기반으로 삼은 이전 문서 리비전 ID를 함께 저장해 리비전 계보를 추적할 수 있어야 한다.
7. 문서 리비전에는 사람이 확인하기 위한 표시용 순번을 유지한다. 실제 계보 판단은 순번이 아니라 이전 문서 리비전 ID로 한다.
8. 과거 문서 리비전으로 되돌리는 동작만으로는 새 문서 리비전을 만들지 않는다.
9. 되돌린 문서 상태에서 수정 후 저장하면 새 문서 리비전을 만들고, 그 새 리비전의 이전 문서 리비전 ID는 되돌린 리비전을 가리킨다.
10. 새 문서를 생성하는 즉시 빈 첫 문서 리비전(`v1`)을 만든다.
11. 서로 다른 템플릿 카테고리로 문서를 이동한 결과와 같은 문서 상태 변경도 새 문서 리비전으로 기록한다.
12. 문서에 직접 추가한 섹션의 순서는 드래그가 아니라 위·아래 이동 버튼으로 조정한다.
13. 문서 삭제는 소프트 딜리트가 필수다. 삭제된 문서는 휴지통으로 이동하고, 문서 리비전과 연결 정보는 보존하며 관리자가 복구할 수 있어야 한다.
14. 휴지통 문서를 복구하면 삭제 전의 위키링크, 관계, 태그 연결도 모두 자동으로 복구한다.
15. 삭제된 문서를 가리키는 위키링크는 현재 문서와 공개 문서에서 ‘삭제됨’으로 표시하고 이동할 수 없게 한다. 관리자는 이 상태에서 복구 기능을 사용할 수 있어야 한다.
16. 삭제된 문서의 관계 참조는 일반 뷰어에게 노출하지 않는다. 관리자에게만 ‘삭제된 문서’ 표시와 복구 기능을 제공한다.
17. 문서는 창작 세계관 안에서의 시작·종료 시점을 각각 선택적으로 가진다. 세계관마다 날짜·시대·연표의 표기 방식이 다르므로, 두 값은 날짜·시간 형식으로 제한하지 않는 문자열로 기록하고 비워 둘 수 있다. 이는 서비스가 자동 기록하는 생성·수정 시각과 별개다.
18. 첫 버전에서는 관리자가 `저장` 버튼을 눌렀을 때만 문서를 저장하고 새 문서 리비전을 만든다.
19. 관계는 여러 문서가 함께 참여하는 별도 데이터로 관리한다. 문서 리비전에는 관계 참여 상태를 보존하지 않으며, 과거 문서 리비전을 복원해도 관계의 현재 참여·수정·삭제 상태는 바꾸지 않는다.
20. 첫 버전에서는 문서 작성 중 입력 내용을 임시 초안으로 자동 저장하지 않는다. `저장` 버튼을 누르기 전 입력 내용은 문서·문서 리비전·별도 초안 데이터로 보존하지 않는다.

### 공개와 뷰어

1. 새 문서는 기본적으로 비공개다. 관리자가 명시적으로 공개한 문서만 로그인 없는 뷰어에게 노출한다.
2. 공개 문서를 수정해 저장한 새 문서 리비전은 즉시 뷰어에게 노출하지 않는다. 관리자가 선택한 문서 리비전을 별도로 공개 반영할 때만 뷰어에게 표시한다.
3. 공개 문서는 현재 공개 중인 문서 리비전과 그 리비전이 참조한 템플릿 리비전으로 렌더링한다. 템플릿을 수정해도 새 문서 리비전을 공개 반영하기 전에는 뷰어 화면이 바뀌지 않는다.
4. 문서를 처음 공개하거나 공개본을 갱신할 때 관리자가 공개할 문서 리비전을 직접 선택한다. 최신 리비전을 기본으로 제안하되, 이전 안정 리비전도 선택할 수 있어야 한다.
5. 공개 문서를 비공개로 전환하면 즉시 뷰어에게서 숨긴다. 기존 공개 리비전 정보는 내부에 보존해 같은 리비전을 다시 공개할 수 있어야 한다.
6. 뷰어는 리비전 이력, 리비전 목록, 과거 본문을 볼 수 없다. 현재 공개되어 표시되는 문서만 열람할 수 있다.
7. 뷰어는 공개 월드·프로젝트·카테고리 목록과 검색에서 공개 문서를 탐색할 수 있고, 태그 검색도 사용할 수 있다. 비공개 문서는 목록과 검색 결과에 노출하지 않는다.
8. 공개 문서 검색은 문서상 이름, 표시 이름, 태그, 섹션 본문 전체를 대상으로 한다.
9. 뷰어의 공개 문서 검색은 월드나 프로젝트에 제한하지 않는다. 공개된 모든 월드·프로젝트의 문서를 한 번에 검색하고 열람할 수 있다.
10. 공개 문서의 표준 주소는 `/월드코드/프로젝트코드/docs/문서이름` 구조를 사용한다. 문서 이름에는 슬래시를 사용할 수 있으며, `docs` 뒤의 문서 이름은 최대 3개 경로 구간으로 구성한다. 이 구간은 폴더가 아니라 문서상 이름의 일부이며, 별도 폴더 데이터·권한·카테고리 구조를 만들지 않는다. 월드 코드와 프로젝트 코드는 UUID와 별도로 공개 주소에 노출하는 변경 불가 슬러그이며, 주소에서 범위를 식별한다. 월드 또는 프로젝트를 만드는 관리자가 생성 시 직접 입력하며, 월드 슬러그는 서비스 전체에서, 프로젝트 슬러그는 같은 월드 안에서 중복할 수 없다.
11. 문서상 이름이 바뀌면 공개 문서 주소도 새 문서상 이름으로 바뀐다. 이전 공개 주소는 별도 보존·리다이렉트 없이 404로 처리한다.
12. 월드·프로젝트 슬러그에는 한글, 영문 대소문자, 숫자, 하이픈을 허용한다. 경로 구분 기호인 슬래시와 URL 예약 문자는 허용하지 않는다. 문서상 이름의 슬래시는 최대 3개 구간을 구분하는 용도로만 허용한다.
13. 월드·프로젝트 슬러그는 영문 대소문자를 구분하지 않는다. 대소문자만 다른 슬러그는 중복으로 처리하며, 공개 주소 해석도 대소문자를 구분하지 않는다.
14. 뷰어와 관리자 등 모든 프론트엔드 라우트는 월드·프로젝트 범위를 같은 공개 슬러그로 식별한다. 프론트엔드 라우트에 내부 UUID를 노출하지 않는다.

### 관리자와 권한

1. 운영자와 관리자는 월드를 만들 수 있다. 관리자는 자신이 만든 월드만 관리하고, 운영자는 모든 월드를 관리한다.
2. 일반 회원 가입은 제공하지 않는다. 관리자 희망자가 권한을 요청하면 운영자가 승인 후 관리자 계정을 생성하고, 승인된 관리자만 로그인할 수 있다.
3. 관리자가 부관리자를 초대할 때는 실명이 아닌 표시 이름과 이메일을 입력한다.
4. 초대 이메일과 일치하는 기존 계정이 있으면 해당 계정을 초대한다. 기존 계정이 없으면 초대 이메일을 발송하고, 수신자가 초대 링크 절차를 진행해 계정을 생성한 뒤 부관리자로 참여한다.
5. 새 관리자 계정과 초대로 새로 생성되는 부관리자 계정에는 임시 비밀번호를 자동 발급한다. 임시 비밀번호는 계정 생성 이메일에서 확인할 수 있고, 최초 로그인 시 반드시 비밀번호를 변경해야 한다. 이미 존재하는 계정을 부관리자로 초대할 때는 기존 비밀번호를 그대로 사용하며 임시 비밀번호를 다시 발급하거나 변경을 요구하지 않는다.
6. 한 계정은 월드마다 서로 다른 역할을 가질 수 있다. 운영자는 모든 월드의 최상위 역할이며, 관리자는 한 월드에서 관리자이면서 다른 월드에서는 부관리자가 될 수 있다.
7. 관리 권한은 월드, 프로젝트, 부관리자 초대, 카테고리, 템플릿, 문서, 태그, 관계의 8개 관리 대상별 생성·수정·삭제로 구성한다. 관계 관리는 시스템 기본 관계 유형의 월드별 활성화·비활성화, 사용자 정의 관계 유형과 역할·허용 카테고리 관리, 실제 관계 인스턴스 관리를 함께 뜻한다. 부관리자에게는 월드 관리, 부관리자 초대, 관계 관리를 제외한 관리 대상의 세부 권한을 사람마다 개별 설정한다.
8. 부관리자에게 삭제 권한을 별도로 부여할 수 있다. 부관리자는 부여받은 권한 범위 안에서는 자유롭게 작업하고, 범위 밖 기능은 사용할 수 없다.
9. 부관리자는 소속 월드의 월드 관리를 할 수 없지만 프로젝트 관리는 할 수 있다.
10. 운영자가 계정에 월드 관리 권한을 별도로 부여하면, 그 계정은 새 월드를 만들고 자신이 만든 월드를 관리할 수 있다. 기존에 부관리자로 소속된 월드에서는 계속 부관리자 권한만 적용한다.
11. 부관리자의 프로젝트 관리 권한은 관리자가 선택한 프로젝트에만 적용한다. 프로젝트 관리 권한은 프로젝트 자체의 생성·수정·삭제만 허용하며, 카테고리·템플릿·문서·태그 같은 프로젝트 소속 항목의 관리 권한을 자동으로 포함하지 않는다.
12. 부관리자의 카테고리, 템플릿, 문서 관리 권한은 각각 대상 프로젝트를 선택해 개별 제한한다.
13. 문서 작성·수정 권한에는 해당 문서의 기존 태그 연결·해제와 새 태그 입력 권한이 자동으로 포함된다. 새 태그를 입력하면 월드 공용 태그 목록에 자동으로 추가한다.
14. 새 태그 생성은 문서 작성·수정 권한과 분리하지 않는다. 별도 태그 관리 권한은 월드 공용 태그 목록의 삭제 같은 목록 정리만 뜻한다.
15. 부관리자에게는 부관리자 초대 권한을 부여하지 않는다. 부관리자 초대와 권한 위임은 관리자와 운영자만 할 수 있다.
16. 부관리자에게는 관계 관리 권한을 부여하지 않는다. 관계 유형과 참여자 역할·허용 카테고리 규칙, 실제 관계 인스턴스는 관리자와 운영자만 관리한다.
17. 부관리자에게는 월드 공용 태그 목록의 삭제 권한을 부여하지 않는다. 태그 목록 정리는 관리자와 운영자만 한다.
18. 부관리자의 권한 변경과 소속 월드 해제는 즉시 적용한다. 이미 로그인한 상태여도 다음 작업부터 변경된 권한으로 검사한다.
19. 관리자·부관리자의 초대, 권한 변경, 소속 해제는 감사 이력으로 남긴다. 이력에는 수행자, 시각, 대상 계정, 변경 전후의 권한·소속 상태를 보존한다.
20. 권한 감사 이력은 운영자는 모든 월드 범위를, 관리자는 자신이 관리하는 월드 범위만 열람할 수 있다. 부관리자는 열람할 수 없다.
21. 수락 전 부관리자 초대는 관리자와 운영자가 취소할 수 있지만, 초대에 포함된 권한과 대상 프로젝트는 변경할 수 없다. 내용을 바꾸려면 기존 초대를 취소하고 새 초대를 보낸다.
22. 부관리자 초대 이메일의 수락 링크는 발송 후 7일 동안만 유효하며, 이후 자동으로 만료된다.
23. 관리자와 부관리자가 비밀번호를 잊으면 등록된 이메일로 재설정 링크를 보내고, 본인이 새 비밀번호를 설정한다. 링크는 발송 뒤 24시간 동안 유효하며, 실제 비밀번호 변경이 완료되기 전에는 같은 링크로 여러 번 접근할 수 있다. 비밀번호 변경이 완료되면 즉시 사용할 수 없다.
24. 비밀번호 재설정은 기존 이메일의 재발송 기능을 두지 않는다. 계정 소유자가 다시 요청하면 새 재설정 요청과 링크를 만들고, 기존 대기 링크는 즉시 무효화한다. 부관리자 초대의 재발송·재초대 정책과는 별도 흐름으로 다룬다.
25. 대기 중인 부관리자 초대는 이메일을 잃었거나 발송에 실패했을 때 같은 이메일로 재발송할 수 있다. 이때 초대 상태·권한·대상 프로젝트와 수락 링크는 그대로 유지한다. 초대 내용을 바꾸려는 경우에만 기존 초대를 취소하고 새 초대를 만든다.

### 최초 운영자 생성

1. 서비스 최초 설치 때 최초 운영자 계정을 직접 생성한다. `admins`에는 실제 로그인 계정만 기록하며, 시스템용 가상 계정은 만들지 않는다.
2. 최초 운영자 계정 한 건만 `creatr_id`를 비워 둘 수 있다. 그 이후에 만들어지는 모든 데이터의 `creatr_id`는 기존 로그인 관리자 계정을 기록한다.

### 태그

1. 월드 공용 태그 목록은 기본적으로 태그 이름순으로 정렬한다. 화면 목적에 따라 다른 정렬 기준을 추가할 수 있으며, 이 기본값이 모든 화면의 정렬을 제한하지는 않는다.
2. 현재 문서에서 사용 중인 태그도 삭제할 수 있다. 삭제하면 모든 현재 문서에서 해당 태그 연결을 자동으로 해제하고, 과거 문서 리비전에 보존된 태그 기록은 유지한다.
3. 태그 이름 수정 기능은 제공하지 않는다. 이름을 바꿔야 하면 기존 태그를 삭제하고 새 이름의 태그를 사용한다.
4. 삭제한 태그를 복구하면 삭제 당시 자동 해제한 연관 문서의 태그 연결도 함께 복구한다.
5. 삭제된 태그는 과거 문서 리비전에 이력으로만 남긴다. 해당 리비전이 공개 문서로 표시되는 경우에도 삭제 태그는 노출하거나 검색 대상으로 사용하지 않는다.

### 이름 중복 규칙

1. 같은 월드 안에서는 태그 이름을 중복할 수 없다.
2. 같은 프로젝트 안에서도 표시 이름 중복을 허용한다.
3. 문서 이름 입력 시 같은 표시 이름의 기존 문서를 확인할 수 있어야 한다. 중복된 표시 이름을 사용하려면 관리자가 괄호 안의 구분 표기를 직접 입력해 문서상 이름을 구별한다.
4. 문서상 이름은 괄호 구분 표기까지 포함해 저장하고, 화면에 보이는 표시 이름은 괄호를 제외해 별도로 저장한다. 두 값은 서로 다를 수 있다.
5. 괄호 안의 구분 표기는 프로젝트명이 아니라 관리자가 직접 작성한다.
6. 문서상 이름, 표시 이름, 괄호 구분 표기는 일반 문서 수정 화면에서 변경할 수 없다. 문서 관리 페이지에서만 변경한다.
7. 위키링크는 항상 `[[보여질이름:문서이름]]` 형식으로 작성한다.
8. 위키링크는 섹션 본문 안에서 대상 문서의 내부 ID를 가진 링크 조각으로 저장한다. 화면 표시와 내보내기에서는 항상 `[[보여질이름:문서이름]]` 문자열 형식을 사용한다.
9. 위키링크 문자열과 별도로 연결 대상 문서의 내부 ID를 보관해 문서상 이름이나 표시 이름이 바뀌어도 연결 대상이 끊기지 않게 한다.
10. 위키링크는 같은 월드 안의 모든 프로젝트 문서를 연결할 수 있다. 다른 월드 문서는 위키링크 대상으로 선택할 수 없다.
11. 공개 문서에서 비공개 문서를 가리키는 위키링크는 제목 대신 ‘비공개 문서’로 표시한다. 뷰어가 클릭하면 접근 권한 없음으로 처리한다.
12. 공개 문서의 역링크 목록에서 비공개 문서는 ‘비공개 문서’로 표시한다. 뷰어가 클릭하면 접근 권한 없음으로 처리한다.
13. 대상 문서의 이름이 바뀌면 현재 문서와 공개 문서는 최신 이름으로 위키링크를 표시하고, 과거 문서 리비전은 저장 당시 이름으로 표시한다.
14. 문서에는 이 문서를 가리키는 다른 문서를 자동으로 보여 주는 역링크 목록을 제공한다.
15. 문서상 이름에 포함하는 슬래시 구분은 최대 3개 구간까지만 허용하며, 이는 문서 이름의 표현일 뿐 실제 폴더·상위 문서·권한 범위를 뜻하지 않는다.
