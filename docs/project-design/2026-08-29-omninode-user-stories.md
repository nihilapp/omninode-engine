# 옴니노드 사용자 스토리 목록

> 분류: 프로젝트 설계
>
> 근거: 마스터의 기초 기획과 `2026-08-29-omninode-requirements-decisions.md`의 1차 기획 확정 사항
>
> 범위: 아래 `확정 사용자 스토리`는 현재 지원해야 할 기능의 목록이다. 구현 순서나 구현 승인 목록은 아니다.

## 우선순위 지표

- **P0 — 핵심 작성 기반:** 월드 설정을 구조화해 작성·보존하는 최소 기능이다. 이 기능 없이 옴니노드를 노션의 대체 도구로 사용할 수 없다.
- **P1 — 기본 서비스 완성:** 공동 관리와 공개 열람을 포함해, 작성한 설정을 실제 서비스로 운영하기 위한 기능이다.
- **P2 — 안전한 운영과 예외 처리:** 변경·삭제·비활성화처럼 기존 데이터를 위험 없이 관리하기 위한 기능이다.

우선순위는 기능의 필요성 순서이며, 구현 승인이나 실제 개발 일정은 아니다. 아래 인덱스는 우선순위 순서이고, 뒤의 상세 목록은 도메인별 추적을 위해 유지한다.

## 우선순위별 사용자 스토리 인덱스

### P0 — 핵심 작성 기반

- 월드·프로젝트 생성과 이름 관리: US-01, US-02, US-16, US-17, US-20
- 3단계 카테고리와 템플릿 강제 구조: US-21 ~ US-25, US-30 ~ US-33
- 섹션별 문서 작성과 리비전·위키링크: US-36 ~ US-40, US-42, US-45 ~ US-49
- 월드 관계 유형과 관계 인스턴스 작성: US-53 ~ US-57

### P1 — 기본 서비스 완성

- 부관리자 초대와 개별 권한 운영: US-03 ~ US-10, US-12 ~ US-14
- 템플릿 리비전과 비활성 템플릿의 기존 문서 유지: US-34, US-35, US-68
- 공개 문서 반영과 로그인 없는 뷰어 열람·검색: US-61 ~ US-67, US-71

### P2 — 안전한 운영과 예외 처리

- 권한 감사와 계정 탈퇴: US-11, US-15
- 월드·프로젝트의 삭제·복구와 동명 항목 처리: US-18, US-19
- 카테고리 이동, 점검, 공개 중단 처리: US-26 ~ US-29
- 기존 문서의 템플릿 변경 반영과 문서 삭제·복구: US-41, US-43, US-44, US-69
- 태그 삭제·복구와 이름 교체: US-50 ~ US-52, US-70
- 관계 유형 비활성화·변경과 관계 변경 이력: US-58 ~ US-60

## 확정 사용자 스토리 상세

### 계정과 권한

- US-01. 운영자로서 관리자 권한 요청을 검토하고 계정을 생성하여, 승인된 창작자만 서비스를 관리하게 하고 싶다.
- US-02. 관리자로서 내가 만든 월드만 관리하고, 운영자로서 모든 월드를 관리하고 싶다.
- US-03. 관리자로서 월드별 부관리자를 표시 이름과 이메일로 초대하여, 공동 관리자를 참여시키고 싶다.
- US-04. 초대받는 사람으로서 기존 계정이 있으면 현재 계정으로 초대를 수락하고, 계정이 없으면 초대 링크로 계정을 만들고 싶다.
- US-05. 새 관리자 또는 새 부관리자로서 이메일의 임시 비밀번호로 처음 로그인한 뒤, 반드시 내 비밀번호를 변경하고 싶다.
- US-06. 기존 계정 소유자로서 다른 월드의 부관리자 초대를 수락할 때 기존 비밀번호를 계속 사용하고 싶다.
- US-07. 관리자로서 부관리자마다 프로젝트·카테고리·템플릿·문서 관리 권한을 개별적으로 부여하고 싶다.
- US-08. 관리자로서 부관리자에게 삭제 권한을 포함하거나 제외하여, 제한된 범위 안에서만 작업하게 하고 싶다.
- US-09. 운영자로서 계정에 월드 관리 권한을 부여하여, 그 계정이 새 월드를 만들고 자신이 만든 월드를 관리하게 하고 싶다.
- US-10. 관리자로서 부관리자의 권한 또는 월드 소속을 바꾸면 이미 로그인한 상태에도 즉시 반영하고 싶다.
- US-11. 운영자 또는 관리자로서 초대·권한 변경·소속 해제 이력을 확인하여, 누가 어떤 권한을 바꿨는지 추적하고 싶다.
- US-12. 관리자 또는 운영자로서 대기 중인 부관리자 초대를 취소하고, 권한이나 대상 프로젝트를 바꾸려면 새 초대를 보내고 싶다.
- US-13. 초대받는 사람으로서 7일 안에 초대 링크를 사용하여 참여하고, 초대 이메일을 잃었을 때 관리자가 같은 대기 초대를 재발송해 주기를 원한다.
- US-14. 관리자 또는 부관리자로서 비밀번호를 잊었을 때 등록된 이메일로 직접 재설정을 요청하고, 실제 변경을 마칠 때까지 24시간 동안 같은 재설정 링크에 다시 접근하고 싶다. 다시 요청하면 새 링크를 받고 기존 링크는 무효화하고 싶다.
- US-15. 계정 소유자로서 탈퇴를 요청하면 즉시 서비스 접근이 중단되지만, 7일 동안 탈퇴 안내 이메일의 전용 링크로 내가 소유한 월드 전체와 다른 월드에서 내가 작성한 문서·관계를 Markdown·JSON이 담긴 ZIP 파일로 내려받고, 링크를 잃으면 같은 이메일로 재발송받고 싶다. 내 소유 월드에 부관리자가 있으면 탈퇴를 확정할 때 지정한 부관리자에게 그 월드를 넘기고 싶다.

### 월드와 프로젝트

- US-16. 관리자로서 하나 이상의 월드를 만들고, 각 월드 안에 작품 단위의 프로젝트를 만들고 싶다.
- US-17. 관리자로서 월드·프로젝트를 만들 때 한글, 영문 대소문자, 숫자, 하이픈으로 된 공개 주소용 슬러그를 직접 입력하고, 대소문자만 다른 슬러그도 중복으로 처리하며, 월드 슬러그는 서비스 전체에서, 프로젝트 슬러그는 같은 월드 안에서 중복하지 않고 싶다. 같은 관리자가 만든 월드 안에서는 월드 이름을 중복하지 않고, 같은 월드 안에서는 프로젝트 이름을 중복하지 않고 싶다.
- US-18. 관리자로서 월드 또는 프로젝트를 삭제해도 하위 데이터를 보존하고, 필요할 때 원래 상태로 복구하고 싶다.
- US-19. 관리자로서 같은 이름의 삭제된 항목이 있을 때 기존 항목을 복구할지 별개의 새 항목을 만들지 선택하고 싶다.
- US-20. 관리자로서 새 월드와 프로젝트를 만들면 기본 제공 관계 유형·카테고리·템플릿을 활성화된 상태로 시작하고 싶다.

### 카테고리와 템플릿

- US-21. 관리자로서 프로젝트마다 최대 3단계의 카테고리 트리를 만들고, 사용자 정의 카테고리를 대분류 또는 기본 카테고리 아래에 만들며, 문서에는 필요한 깊이까지만 카테고리를 지정하고 싶다.
- US-22. 관리자로서 같은 부모 아래의 카테고리 이름 중복을 막고, 위·아래 이동으로 표시 순서를 조정하고 싶다.
- US-23. 관리자로서 대분류 카테고리에 템플릿을 연결하고, 하나의 템플릿을 여러 대분류에 연결하고 싶다.
- US-24. 관리자로서 템플릿이 연결되지 않은 대분류에는 문서를 만들지 못하게 하여, 문서 구조의 일관성을 유지하고 싶다.
- US-25. 관리자로서 템플릿이 연결된 같은 카테고리 안의 모든 문서가 같은 템플릿을 사용하게 하고 싶다.
- US-26. 관리자로서 문서를 다른 템플릿 카테고리로 옮길 때 기존 섹션별로 추가 섹션 유지 또는 삭제를 직접 선택하고 싶다.
- US-27. 관리자로서 사용 중인 카테고리를 비활성화해 새 문서 작성과 카테고리 변경에서는 막되, 기존 문서의 분류는 유지하고 싶다.
- US-28. 관리자로서 카테고리를 다른 상위 카테고리 아래로 옮기고, 영향받는 문서·템플릿·관계 구조를 직접 점검하고 싶다.
- US-29. 관리자로서 카테고리 이동의 점검 대상이 공개 중이면 즉시 비공개로 전환하고, 직접 점검 완료 처리 전에는 다시 공개하지 못하게 하고 싶다.
- US-30. 관리자로서 템플릿의 첫 필수 섹션을 항상 `개요`로 두고, 나머지 섹션은 선택 섹션으로 구성하고 싶다.
- US-31. 관리자로서 템플릿의 선택 섹션을 `개요` 아래 어디에나 추가하고, 위·아래 이동으로 순서를 조정하고 싶다.
- US-32. 관리자로서 템플릿 섹션 이름의 중복과 섹션 삭제를 막고, 다른 구조가 필요하면 새 템플릿을 만들고 싶다.
- US-33. 관리자로서 템플릿 섹션의 코드가 자동 생성되고 누구도 바꿀 수 없게 하여, 문서의 섹션 참조를 안정적으로 유지하고 싶다.
- US-34. 관리자로서 템플릿을 수정할 때마다 템플릿 리비전을 남기고, 이전 리비전으로 되돌리더라도 새 리비전을 만들지 않고 싶다.
- US-35. 관리자로서 사용 중인 템플릿을 비활성화해 새 문서 생성과 새 카테고리 연결만 막고, 기존 문서와 이력은 계속 렌더링하고 싶다.
- US-68. 관리자로서 문서의 연결 템플릿 리비전이 현재 적용 중인 템플릿 리비전과 다른 문서를 문서 관리 목록에서 `템플릿 점검 필요`로 확인하고, 현재 템플릿 구조를 적용해 저장하면 이 표시가 자동으로 해제되게 하고 싶다.

### 문서, 리비전, 위키링크

- US-36. 관리자로서 문서를 섹션별 본문으로 작성하고, 문서 생성 시 비어 있는 첫 리비전을 자동으로 만들고 싶다.
- US-37. 관리자로서 문서 내용·카테고리·태그·이름·세계관 안의 시작·종료 시점 등 문서 상태를 `저장`할 때마다만 새 문서 리비전을 남기고, 첫 버전에서는 자동 임시 초안을 만들지 않고 싶다.
- US-38. 관리자로서 문서 리비전이 이전 리비전과 당시의 템플릿 리비전을 참조하게 하여, 과거 상태를 정확히 확인하고 싶다.
- US-39. 관리자로서 과거 문서 리비전으로 되돌아가되, 되돌린 상태를 다시 수정·저장할 때만 새 리비전을 쌓고 싶다.
- US-40. 관리자로서 문서의 현재 화면은 최신 템플릿 구조를 따르고, 과거 리비전은 당시 템플릿 구조로 보고 싶다.
- US-41. 관리자로서 기존 문서가 쓰는 템플릿에 선택 섹션을 추가해도, 그 문서를 수정·저장하기 전에는 읽기 화면에 새 섹션이 나타나지 않게 하고 싶다.
- US-42. 관리자로서 문서에 템플릿 외의 추가 섹션을 만들고, 필수 섹션 사이 또는 끝에 위·아래 이동으로 배치하고 싶다.
- US-43. 관리자로서 문서를 소프트 딜리트하고, 리비전·위키링크·관계·태그 연결을 보존한 채 복구하고 싶다.
- US-44. 관리자로서 삭제된 문서를 가리키는 위키링크를 `삭제됨`으로 확인하고, 필요하면 문서를 복구하고 싶다.
- US-45. 관리자로서 같은 프로젝트 안에서 표시 이름이 같은 문서를 만들 때, 괄호 구분 표기를 직접 입력해 문서상 이름을 구별하고 싶다. 문서상 이름에는 폴더 구조와 무관한 슬래시 구분을 최대 3개 구간까지 사용하고 싶다.
- US-46. 관리자로서 일반 문서 편집과 분리된 관리 페이지에서만 문서상 이름·표시 이름·괄호 구분 표기를 바꾸고 싶다.
- US-47. 관리자로서 `[[보여질이름:문서이름]]` 형식으로 위키링크를 작성하고, 대상 문서의 이름이 바뀌어도 연결이 끊기지 않게 하고 싶다.
- US-48. 관리자로서 같은 월드의 다른 프로젝트 문서에도 위키링크를 만들고, 내 문서를 가리키는 역링크를 보고 싶다.
- US-69. 관리자로서 문서 리비전을 복원해도 여러 문서가 함께 참여하는 관계의 현재 상태는 바뀌지 않게 하고 싶다.

### 태그와 관계

- US-49. 관리자로서 문서를 작성·수정하며 기존 태그를 연결·해제하거나 새 태그를 입력하고, 새 태그가 월드 공용 목록에 자동 등록되게 하고 싶다.
- US-50. 관리자로서 월드 공용 태그 목록을 이름순으로 보고, 사용 중인 태그를 삭제하면 현재 문서 연결을 자동 해제하고 싶다.
- US-51. 관리자로서 삭제한 태그를 복구할 때 이전에 자동 해제된 문서 태그 연결도 함께 복구하고 싶다.
- US-52. 관리자로서 태그 이름을 수정하지 않고, 이름을 바꿔야 하면 기존 태그를 삭제한 뒤 새 태그를 사용하고 싶다.
- US-70. 관리자로서 삭제된 태그가 과거 공개 문서 리비전에 기록되어 있어도 뷰어에게 표시되거나 검색되지 않게 하고 싶다.
- US-53. 관리자로서 월드마다 기본 관계 유형을 활성화·비활성화하고, 필요한 사용자 정의 관계 유형을 추가하고 싶다.
- US-54. 관리자로서 관계 유형마다 참여자 역할, 역할별 허용 카테고리, 역할 반복 가능 여부를 정의하고 싶다.
- US-55. 관리자로서 2~4개의 문서와 각 참여자 역할을 지정해 하나의 관계를 만들고, 문서 위치에 따라 정방향·역방향으로 보고 싶다.
- US-56. 관리자로서 관계에 선택적 시작·종료 시점, 설명, 관련 문서 링크를 기록하고 싶다.
- US-57. 관리자로서 같은 관계 유형·참여 문서·참여자 역할 구성이 같은 중복 관계를 만들지 못하게 하고 싶다.
- US-58. 관리자로서 관계 유형을 비활성화하면 그 유형의 기존 관계도 끊고, 다시 활성화하더라도 필요한 관계는 새로 만들고 싶다.
- US-59. 관리자로서 관계 수정·삭제의 변경 이력을 확인하되, 관계 리비전 복원 기능은 사용하지 않고 싶다.
- US-60. 관리자로서 사용된 사용자 정의 관계 유형의 구조는 바꾸지 않고, 다른 구조가 필요하면 새 관계 유형을 만들고 싶다.

### 공개와 뷰어

- US-61. 관리자로서 새 문서를 기본 비공개로 만들고, 원하는 문서 리비전만 선택해 공개하고 싶다.
- US-62. 관리자로서 공개 문서를 수정해도 명시적으로 새 리비전을 공개 반영하기 전에는 뷰어 화면이 바뀌지 않게 하고 싶다.
- US-63. 관리자로서 공개 문서를 비공개로 전환하면 즉시 숨기고, 이전 공개 리비전을 보존해 다시 공개하고 싶다.
- US-64. 뷰어로서 로그인 없이 현재 공개된 문서만 읽고, 문서 리비전 이력이나 과거 본문은 보지 않고 싶다.
- US-65. 뷰어로서 공개된 모든 월드·프로젝트의 문서를 월드 제한 없이 검색하고 열람하고 싶다.
- US-66. 뷰어로서 공개 문서의 이름·태그·섹션 본문으로 검색하고, 공개 문서만 결과에서 보고 싶다.
- US-67. 뷰어로서 공개 문서 안의 비공개 문서 관계·위키링크를 `비공개 문서`로 확인하고, 접근이 막힌 상태임을 알고 싶다.
- US-71. 뷰어로서 UUID와 별도의 월드·프로젝트 슬러그를 사용하는 `/월드코드/프로젝트코드/docs/문서이름` 주소로 공개 문서를 바로 열람하고 싶다. 문서 이름은 `docs` 뒤 최대 3개 경로 구간으로 표현할 수 있으며, 문서상 이름이 바뀌어 이전 주소로 접근하면 404를 확인하고 싶다.

## 추가 검토 필요 기능

아래 기능은 기초 기획의 목표를 돕지만, 1차 기획에서 지원 여부·동작 규칙을 확정하지 않았다. 위 확정 사용자 스토리에 포함하지 않는다.

- 노션 사용을 중단하고 옴니노드를 사용하려는 것은 이 서비스의 도입 목적이다. 따라서 노션 데이터 이관 기능은 별도 지원 기능 후보로 목록화하지 않는다.
- 후보-02. 관리자로서 문서·관계·태그 등 월드 데이터를 내보내거나 백업하고 싶을 수 있다.
  - 검토 이유: 데이터 보존 원칙은 확정했지만, 사람이 사용하는 내보내기·백업 기능은 정해지지 않았다.
## 사용자 스토리 범위 밖의 운영 결정

- 서비스 최초 설치 시에만 최초 운영자 계정을 직접 생성한다. 이 계정의 `creatr_id`만 비워 둘 수 있으며, 이후 생성되는 모든 데이터에는 실제 로그인 관리자 ID를 생성자로 기록한다.
- 탈퇴한 계정이 다른 관리자의 월드에 작성한 문서·관계는 해당 월드에 그대로 남긴다. 탈퇴 계정의 권한·소속·로그인 정보는 제거하고, 작성자 표시가 필요할 때만 `탈퇴한 관리자`로 표시한다.
- 탈퇴 계정이 소유한 월드에 부관리자가 있으면 탈퇴자가 지정한 한 명을 탈퇴 확정 즉시 관리자로 승격하고 월드 소유권을 넘긴다.
