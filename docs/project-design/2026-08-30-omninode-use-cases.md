# 옴니노드 유스케이스

> 분류: 프로젝트 설계
>
> 근거: `2026-08-29-omninode-user-stories.md`, `2026-08-29-omninode-requirements-decisions.md`
>
> 범위: 사용자 스토리의 목적을 실제 사용 흐름으로 구체화한다. 화면, API, 테이블·컬럼, ORM, 데이터베이스 구현은 포함하지 않는다.

## 작성 원칙

- 각 유스케이스는 하나의 사용자 목적과 대응하는 사용자 스토리를 가진다.
- 기본 흐름은 사용자의 행동과 시스템 반응만 서술한다.
- 대안·예외는 확정된 정책에서 필요한 경우에만 기록한다.
- 이 문서에서 새 요구사항이나 정책을 확정하지 않는다.

## 계정·권한·초대

### UC-01. 월드 관리 권한을 부여한다

- **관련 사용자 스토리:** US-01, US-02, US-09
- **행위자:** 운영자
- **목적:** 계정이 자신의 월드를 만들고 관리할 수 있게 한다.
- **사전 조건:** 운영자가 대상 계정을 관리할 수 있다.
- **기본 흐름:** 운영자가 대상 계정의 현재 역할과 권한을 확인하고 월드 관리 권한을 부여한다. 시스템은 권한을 반영하고 이후 대상 계정이 월드를 만들 수 있게 한다.
- **결과:** 대상 계정은 새 월드를 만들고 자신이 만든 월드를 관리할 수 있다.
- **관련 데이터:** 계정, 역할, 전역 월드 관리 허가

### UC-02. 부관리자를 초대한다

- **관련 사용자 스토리:** US-03, US-04, US-05, US-06, US-13
- **행위자:** 관리자 또는 운영자
- **목적:** 다른 사람에게 월드의 제한된 관리 권한을 부여한다.
- **사전 조건:** 행위자에게 부관리자 초대 권한이 있고, 대상 월드가 존재한다.
- **기본 흐름:** 행위자가 표시 이름·이메일·프로젝트 범위·세부 허가를 정해 초대한다. 시스템은 이메일에 연결된 기존 계정을 확인하고 대기 초대를 만든다. 기존 계정이면 해당 계정이 초대를 수락해 기존 인증 정보를 유지하고, 계정이 없으면 초대 수락 과정에서 계정을 만들고 임시 비밀번호를 발급한다.
- **대안 흐름:** 초대 이메일을 잃었거나 발송에 실패하면 행위자가 같은 대기 초대를 재발송한다.
- **예외 흐름:** 같은 월드와 이메일의 대기 초대가 있으면 새 초대를 중복으로 만들 수 없다. 권한이나 프로젝트 범위를 바꾸려면 기존 대기 초대를 취소하고 새로 초대해야 한다.
- **결과:** 수락한 사람은 해당 월드의 부관리자가 되고, 초대 당시 정한 허가를 가진다.
- **관련 데이터:** 계정, 월드 소속 역할, 세부 허가, 대기 초대, 임시 비밀번호 상태

### UC-03. 부관리자의 권한 또는 소속을 조정한다

- **관련 사용자 스토리:** US-07, US-08, US-10, US-12
- **행위자:** 관리자 또는 운영자
- **목적:** 부관리자가 맡아야 할 범위와 행동을 실제 역할에 맞게 유지한다.
- **사전 조건:** 대상 계정이 해당 월드의 부관리자다.
- **기본 흐름:** 행위자가 부관리자의 프로젝트 범위와 관리 대상별 생성·수정·삭제 허가를 확인하고 필요한 값을 바꾸거나 소속을 해제한다. 시스템은 변경 전후 상태를 남기고 다음 작업부터 바뀐 권한을 적용한다.
- **결과:** 부관리자는 부여된 범위 안에서만 작업하거나, 소속 해제 뒤 해당 월드에 접근하지 못한다.
- **관련 데이터:** 월드 소속 역할, 프로젝트 범위별 허가, 권한 감사 이력

### UC-04. 비밀번호를 재설정한다

- **관련 사용자 스토리:** US-14
- **행위자:** 관리자 또는 부관리자
- **목적:** 등록 이메일을 통해 계정 접근을 다시 확보한다.
- **기본 흐름:** 행위자가 비밀번호 재설정을 요청한다. 시스템은 24시간 동안 유효한 재설정 링크를 발송한다. 행위자는 실제 변경을 완료할 때까지 같은 링크에 다시 접근할 수 있고, 새 비밀번호를 확정하면 시스템은 기존 링크를 즉시 완료 상태로 처리한다.
- **대안 흐름:** 행위자가 재설정을 다시 요청하면 시스템은 새 링크를 만들고 이전 대기 링크를 무효화한다.
- **결과:** 계정의 비밀번호가 새 값으로 바뀐다.
- **관련 데이터:** 계정 인증 정보, 비밀번호 재설정 요청, 만료·완료·무효 상태

### UC-05. 계정을 탈퇴하고 데이터를 내려받는다

- **관련 사용자 스토리:** US-15
- **행위자:** 계정 소유자
- **목적:** 서비스 이용을 끝내기 전에 자신이 만든 설정 데이터를 보관한다.
- **사전 조건:** 탈퇴자가 소유한 월드 중 부관리자가 있는 월드는 승계할 부관리자를 지정할 수 있다.
- **기본 흐름:** 계정 소유자가 탈퇴를 확정한다. 시스템은 즉시 일반 서비스 접근을 차단하고, 소유 월드별 지정 부관리자에게 소유권을 넘긴다. 시스템은 탈퇴 확정 시점의 대상 데이터를 보존해 7일 동안 이메일 전용 링크로 반복 내려받을 수 있게 한다.
- **대안 흐름:** 전용 링크를 잃으면 같은 이메일로 새 링크를 발급받는다. 새 링크가 발급되면 이전 링크는 즉시 무효가 된다.
- **결과:** 부관리자가 없는 소유 월드는 7일 뒤 계정과 함께 완전 삭제된다. 다른 관리자의 월드에 남긴 문서·관계는 유지되고 작성자 참조만 제거된다.
- **관련 데이터:** 계정 탈퇴 상태, 데이터 내려받기 스냅샷, 월드 소유권 승계, 계정이 만든 문서·관계

## 월드·프로젝트

### UC-06. 월드를 만든다

- **관련 사용자 스토리:** US-16, US-17, US-20
- **행위자:** 월드 생성 권한이 있는 관리자
- **목적:** 하나의 창작 세계관을 관리할 최상위 범위를 만든다.
- **기본 흐름:** 행위자가 월드 이름과 한글, 영문 대소문자, 숫자, 하이픈으로 된 공개 주소용 슬러그를 직접 입력한다. 시스템은 같은 관리자가 만든 활성 월드와 삭제된 동명 월드, 영문 대소문자를 구분하지 않는 서비스 전체의 중복 월드 슬러그를 확인한다. 생성이 가능하면 월드를 만들고 기본 관계 유형을 사용할 수 있는 상태로 준비한다.
- **대안 흐름:** 같은 이름의 삭제 월드가 있으면 행위자는 기존 월드를 복구하거나 별도 월드를 새로 만든다.
- **결과:** 행위자는 새 월드의 관리자가 된다.
- **관련 데이터:** 월드, 월드 소유자, 관리자 역할·허가, 기본 관계 유형 참조

### UC-07. 프로젝트를 만든다

- **관련 사용자 스토리:** US-16, US-17, US-20
- **행위자:** 프로젝트 생성 권한이 있는 관리자 또는 부관리자
- **목적:** 월드 안에서 작품 단위의 설정 범위를 만든다.
- **사전 조건:** 대상 월드에 프로젝트 관리 권한이 있다.
- **기본 흐름:** 행위자가 프로젝트 이름과 한글, 영문 대소문자, 숫자, 하이픈으로 된 공개 주소용 슬러그를 직접 입력한다. 시스템은 같은 월드의 활성·삭제 프로젝트 이름과 영문 대소문자를 구분하지 않는 중복 프로젝트 슬러그를 확인한다. 생성이 가능하면 프로젝트와 기본 카테고리·템플릿 참조를 사용할 수 있는 상태로 준비한다.
- **대안 흐름:** 같은 이름의 삭제 프로젝트가 있으면 기존 프로젝트를 복구하거나 별도로 새로 만든다.
- **결과:** 월드 안에 프로젝트가 생기고 설정 문서를 분류할 기반이 마련된다.
- **관련 데이터:** 프로젝트, 기본 카테고리·템플릿 참조, 프로젝트 범위 허가

### UC-08. 월드 또는 프로젝트를 삭제하고 복구한다

- **관련 사용자 스토리:** US-18, US-19
- **행위자:** 삭제·복구 권한이 있는 관리자
- **목적:** 불필요한 범위를 숨기되 하위 설정 데이터를 잃지 않는다.
- **기본 흐름:** 행위자가 월드 또는 프로젝트를 삭제한다. 시스템은 대상만 삭제 상태로 바꾸고 하위 데이터의 자체 상태는 바꾸지 않는다. 행위자가 복구하면 시스템은 이전 접근 상태를 다시 허용한다.
- **결과:** 삭제 기간에는 하위 데이터에 접근할 수 없고, 복구하면 하위 데이터가 이전 상태로 다시 접근 가능해진다.
- **관련 데이터:** 월드 또는 프로젝트의 삭제 상태, 하위 데이터 접근 범위

## 카테고리·템플릿

### UC-09. 프로젝트 카테고리 구조를 관리한다

- **관련 사용자 스토리:** US-21, US-22
- **행위자:** 카테고리 관리 권한이 있는 관리자 또는 부관리자
- **목적:** 설정 문서를 최대 3단계의 일관된 분류 체계로 관리한다.
- **기본 흐름:** 행위자가 대분류 또는 허용된 상위 카테고리 아래에 사용자 정의 카테고리를 만들고, 필요에 따라 위·아래 이동으로 같은 상위 카테고리 안의 순서를 조정한다. 시스템은 깊이와 같은 부모 아래 이름 중복을 확인한다.
- **예외 흐름:** 3단계를 넘는 구조 또는 같은 부모 아래의 동명 카테고리는 만들 수 없다.
- **결과:** 프로젝트에서 선택 가능한 카테고리 트리와 표시 순서가 정리된다.
- **관련 데이터:** 기본·사용자 정의 카테고리, 상위 카테고리, 프로젝트별 사용 상태와 순서

### UC-10. 대분류 카테고리에 템플릿을 연결한다

- **관련 사용자 스토리:** US-23, US-24, US-25
- **행위자:** 카테고리 관리 권한이 있는 관리자 또는 부관리자
- **목적:** 같은 카테고리의 문서가 일관된 구성으로 작성되게 한다.
- **기본 흐름:** 행위자가 대분류 카테고리에 사용할 템플릿을 선택해 연결한다. 시스템은 해당 프로젝트에서 사용할 수 있는 템플릿인지 확인하고 연결을 보존한다.
- **결과:** 해당 대분류와 하위 카테고리에서 새 문서를 만들 때 연결된 템플릿이 강제된다.
- **관련 데이터:** 프로젝트 카테고리, 프로젝트 템플릿 참조, 카테고리-템플릿 연결

### UC-11. 템플릿과 섹션 구성을 만든다

- **관련 사용자 스토리:** US-30, US-31, US-32, US-33, US-34
- **행위자:** 템플릿 관리 권한이 있는 관리자 또는 부관리자
- **목적:** 문서에 적용할 섹션 구조와 그 변경 이력을 관리한다.
- **기본 흐름:** 행위자가 첫 필수 섹션 `개요`를 기준으로 선택 섹션을 추가하고 순서와 레벨을 조정한다. 시스템은 섹션 코드를 자동 생성하고, 저장할 때마다 템플릿 리비전을 남긴다.
- **대안 흐름:** 행위자가 과거 템플릿 리비전을 현재 적용 상태로 되돌릴 수 있다. 시스템은 이 경우 새 템플릿 리비전을 만들지 않는다.
- **예외 흐름:** 섹션 코드 변경·섹션 삭제·`개요` 위의 섹션 추가는 허용하지 않는다. 다른 구조가 필요하면 행위자는 새 템플릿을 만든다.
- **결과:** 템플릿의 현재 구조와 과거 구조가 함께 보존된다.
- **관련 데이터:** 템플릿, 영속 섹션 코드, 템플릿 리비전, 리비전별 섹션 구조

### UC-12. 카테고리 또는 템플릿 사용을 중지한다

- **관련 사용자 스토리:** US-27, US-35
- **행위자:** 카테고리 또는 템플릿 관리 권한이 있는 관리자 또는 부관리자
- **목적:** 새 작성에는 사용하지 않되 기존 설정과 이력을 보존한다.
- **기본 흐름:** 행위자가 카테고리 또는 템플릿을 비활성화한다. 시스템은 새 문서 작성·카테고리 변경·새 연결에 사용할 수 없게 하지만 기존 문서·리비전의 분류와 렌더링은 유지한다.
- **결과:** 기존 데이터는 유지되고 새 사용만 제한된다.
- **관련 데이터:** 프로젝트별 카테고리·템플릿 사용 상태, 기존 문서·리비전

### UC-13. 카테고리 트리를 이동하고 영향을 점검한다

- **관련 사용자 스토리:** US-28, US-29
- **행위자:** 카테고리 관리 권한이 있는 관리자 또는 부관리자
- **목적:** 분류 구조를 바꾸면서 문서·템플릿·관계의 정합성을 직접 확인한다.
- **기본 흐름:** 행위자가 카테고리를 다른 상위 카테고리 아래로 이동한다. 시스템은 영향을 받는 문서·템플릿 연결·관계를 점검 대상으로 표시하고, 공개 문서는 즉시 비공개로 전환한다. 행위자는 각 점검 대상을 직접 확인하고 완료 처리한다.
- **결과:** 모든 점검이 완료된 대상만 다시 공개할 수 있다.
- **관련 데이터:** 카테고리 트리, 점검 상태, 문서 공개 상태, 템플릿 연결, 관계

## 문서·위키링크·태그

### UC-14. 카테고리 기준으로 새 문서를 작성한다

- **관련 사용자 스토리:** US-36, US-37
- **행위자:** 문서 생성 권한이 있는 관리자 또는 부관리자
- **목적:** 연결된 템플릿을 따라 설정 문서를 작성한다.
- **사전 조건:** 선택한 대분류에 사용 가능한 템플릿이 연결돼 있다.
- **기본 흐름:** 행위자가 카테고리를 선택해 문서를 만들고 섹션별 내용과 필요하면 세계관 안의 시작·종료 시점을 작성한다. 시스템은 비어 있는 첫 문서 리비전을 만들고, 저장할 때만 문서 상태와 섹션별 내용을 새 리비전으로 보존한다.
- **예외 흐름:** 템플릿이 연결되지 않은 대분류에서는 문서를 만들 수 없다.
- **결과:** 새 문서는 기본 비공개 상태이며, 저장하지 않은 입력은 보존하지 않는다.
- **관련 데이터:** 문서, 문서 리비전, 적용 카테고리·템플릿 리비전, 섹션별 본문

### UC-15. 문서를 수정하고 리비전을 남긴다

- **관련 사용자 스토리:** US-37, US-38, US-42
- **행위자:** 문서 수정 권한이 있는 관리자 또는 부관리자
- **목적:** 문서 내용과 부가 상태를 변경하면서 과거 상태를 보존한다.
- **기본 흐름:** 행위자가 섹션별 본문, 카테고리, 태그 또는 세계관 안의 시작·종료 시점을 수정해 저장한다. 시스템은 이전 문서 리비전과 당시 템플릿 리비전을 연결한 새 문서 리비전을 만든다.
- **결과:** 저장 시점의 문서 상태와 섹션별 내용이 하나의 리비전으로 보존된다.
- **관련 데이터:** 문서 리비전 계보, 섹션별 본문, 카테고리, 태그, 위키링크

### UC-16. 과거 문서 리비전을 현재 상태로 되돌린다

- **관련 사용자 스토리:** US-39, US-69
- **행위자:** 문서 수정 권한이 있는 관리자 또는 부관리자
- **목적:** 과거 문서 상태를 현재 상태로 다시 사용한다.
- **기본 흐름:** 행위자가 과거 문서 리비전을 선택해 현재 상태로 되돌린다. 시스템은 새 리비전을 만들지 않고 현재 문서가 해당 리비전을 가리키게 한다.
- **대안 흐름:** 되돌린 상태를 수정해 저장하면 시스템은 선택한 과거 리비전을 이전 리비전으로 하는 새 리비전을 만든다.
- **결과:** 관계의 현재 상태는 바뀌지 않고 문서 상태만 되돌아간다.
- **관련 데이터:** 현재 문서 리비전, 문서 리비전 계보, 관계의 독립 현재 상태

### UC-17. 최신 템플릿 구조로 기존 문서를 점검한다

- **관련 사용자 스토리:** US-40, US-41, US-68
- **행위자:** 문서 수정 권한이 있는 관리자 또는 부관리자
- **목적:** 템플릿이 바뀐 뒤에도 기존 문서를 유지하면서 필요한 때 최신 구조를 적용한다.
- **기본 흐름:** 템플릿이 바뀌면 시스템은 이전 템플릿 리비전을 쓰는 문서를 `템플릿 점검 필요`로 표시한다. 행위자가 해당 문서의 수정 흐름에 들어가면 시스템은 최신 템플릿 구조로 내용을 보여 준다. 행위자가 저장하면 최신 구조와 새 섹션 연결을 새 문서 리비전에 보존한다.
- **결과:** 저장 전 읽기·공개 화면은 기존 문서 구조를 유지하고, 저장 뒤 점검 표시는 자동 해제된다.
- **관련 데이터:** 현재 템플릿 리비전, 문서 리비전의 적용 템플릿, 문서 섹션 연결, 점검 상태

### UC-18. 문서를 다른 템플릿 카테고리로 옮긴다

- **관련 사용자 스토리:** US-26
- **행위자:** 문서 수정 권한이 있는 관리자 또는 부관리자
- **목적:** 문서를 더 적절한 분류와 템플릿 구조로 이동한다.
- **기본 흐름:** 행위자가 대상 카테고리를 선택한다. 시스템은 대상 템플릿과 기존 섹션을 비교한다. 행위자는 기존 섹션을 추가 섹션으로 남길지 삭제할지 정하고 저장한다.
- **결과:** 이동 결과와 선택한 섹션 처리는 새 문서 리비전으로 보존된다.
- **관련 데이터:** 문서 리비전, 대상 카테고리, 대상 템플릿 리비전, 섹션별 본문

### UC-19. 문서 이름을 관리하고 위키링크를 유지한다

- **관련 사용자 스토리:** US-45, US-46, US-47, US-48
- **행위자:** 문서 수정 권한이 있는 관리자 또는 부관리자
- **목적:** 동명 문서를 구별하면서 문서 간 연결을 안정적으로 유지한다.
- **기본 흐름:** 행위자가 문서 관리 흐름에서 표시 이름과 괄호 구분 표기를 포함한 문서상 이름을 관리한다. 문서상 이름에는 폴더 구조와 무관한 슬래시 구분을 최대 3개 구간까지 사용할 수 있다. 시스템은 이름 변경 상태를 새 문서 리비전으로 보존한다. 문서 본문에는 `[[보여질이름:문서이름]]` 형식으로 위키링크를 작성한다. 시스템은 대상 문서를 내부 식별자로 연결하고 이름 변경 뒤에도 연결을 유지한다.
- **예외 흐름:** 같은 프로젝트의 활성 문서상 이름은 중복될 수 없다. 표시 이름은 중복될 수 있다.
- **결과:** 같은 월드의 다른 프로젝트 문서에도 연결할 수 있고, 역링크를 확인할 수 있다.
- **관련 데이터:** 문서의 표시·문서상 이름, 위키링크 조각, 대상 문서 참조, 역링크

### UC-20. 문서를 삭제하고 복구한다

- **관련 사용자 스토리:** US-43, US-44
- **행위자:** 문서 삭제·복구 권한이 있는 관리자 또는 부관리자
- **목적:** 문서를 숨기면서 리비전과 연결을 보존한다.
- **기본 흐름:** 행위자가 문서를 삭제한다. 시스템은 문서와 리비전·태그·관계·위키링크 연결을 보존한다. 다른 문서에서 삭제 문서를 가리키면 시스템은 `삭제됨`으로 표시한다. 행위자가 복구하면 시스템은 이전 연결을 다시 사용할 수 있게 한다.
- **결과:** 문서는 삭제 상태와 복구 상태를 오갈 수 있다.
- **관련 데이터:** 문서 삭제 상태, 문서 리비전, 태그 연결, 관계 참여, 위키링크

### UC-21. 문서 태그를 관리한다

- **관련 사용자 스토리:** US-49, US-50, US-51, US-52, US-70
- **행위자:** 문서 수정 권한이 있는 관리자 또는 부관리자, 태그 목록 관리 권한이 있는 관리자 또는 운영자
- **목적:** 문서의 보조 분류와 검색 기준을 최신 상태로 유지한다.
- **기본 흐름:** 문서 작성·수정 중 행위자가 기존 태그를 연결하거나 새 태그를 입력한다. 시스템은 새 태그를 월드 공용 목록에 만들고 저장한 문서 리비전에 태그 연결을 보존한다. 목록 관리 권한자는 사용하지 않을 태그를 삭제하거나 복구할 수 있다.
- **결과:** 삭제 태그는 현재 문서·공개 화면·검색에서 제외되며, 복구하면 자동 해제 전 연결이 다시 표시된다.
- **관련 데이터:** 월드 공용 태그, 문서 리비전별 태그 연결, 태그 삭제 상태

## 관계·공개 열람

### UC-22. 관계 유형과 실제 관계를 관리한다

- **관련 사용자 스토리:** US-53 ~ US-60
- **행위자:** 관계 관리 권한이 있는 관리자 또는 운영자
- **목적:** 월드 안 문서들의 관계를 일관된 규칙으로 만들고 관리한다.
- **기본 흐름:** 행위자가 월드의 기본 관계 유형을 활성화 또는 비활성화하고, 필요한 경우 사용자 정의 관계 유형의 역할·허용 카테고리·역할 반복 규칙을 정한다. 행위자는 활성 관계 유형과 2~4개의 허용 문서, 각 문서의 역할을 선택해 실제 관계를 만든다. 시스템은 참여자 구성 중복과 역할·카테고리 규칙을 확인하고 관계를 하나로 보존한다.
- **대안 흐름:** 행위자는 관계 설명과 관련 문서 링크를 추가하거나 관계를 수정·삭제한다. 시스템은 관계 변경 이력을 남긴다.
- **예외 흐름:** 사용된 사용자 정의 관계 유형의 구조는 바꿀 수 없다. 비활성화한 관계 유형의 기존 관계는 끊긴 기록으로 남고 복구되지 않는다.
- **결과:** 문서 위치에 따라 같은 관계를 정방향 또는 역방향으로 볼 수 있다.
- **관련 데이터:** 기본·사용자 정의 관계 유형, 역할·허용 카테고리, 실제 관계, 참여 문서, 관계 이력

### UC-23. 문서 리비전을 공개하거나 비공개로 전환한다

- **관련 사용자 스토리:** US-61, US-62, US-63, US-64
- **행위자:** 문서 수정 권한이 있는 관리자 또는 부관리자
- **목적:** 뷰어에게 보여 줄 문서 상태를 명시적으로 관리한다.
- **기본 흐름:** 행위자가 문서 리비전 중 뷰어에게 보일 리비전을 선택해 공개한다. 시스템은 선택한 리비전만 공개 화면에 사용한다. 행위자가 공개 문서를 수정해도 새 리비전을 명시적으로 공개하기 전까지 공개 화면은 바뀌지 않는다.
- **대안 흐름:** 행위자가 문서를 비공개로 전환하면 시스템은 즉시 뷰어 열람과 검색에서 제외하되 이전 공개 리비전 선택은 보존한다.
- **결과:** 뷰어는 현재 공개된 문서만 보고 리비전 이력은 볼 수 없다.
- **관련 데이터:** 문서의 공개 상태, 뷰어용 공개 문서 리비전, 문서 리비전

### UC-24. 공개 문서를 검색하고 열람한다

- **관련 사용자 스토리:** US-65, US-66, US-67, US-71
- **행위자:** 뷰어
- **목적:** 로그인 없이 여러 월드의 공개 설정 문서를 찾고 읽는다.
- **기본 흐름:** 뷰어가 이름·태그·섹션 본문으로 공개 문서를 검색하거나 `/월드코드/프로젝트코드/docs/문서이름` 주소로 문서를 연다. 문서 이름은 `docs` 뒤 최대 3개 경로 구간으로 표현할 수 있으며, 이 구간은 폴더가 아니다. 시스템은 월드와 프로젝트 제한 없이 공개 상태인 문서만 보여 준다.
- **예외 흐름:** 공개 문서 안에서 비공개 문서를 가리키는 관계·위키링크는 `비공개 문서`로, 삭제 문서를 가리키는 연결은 `삭제됨`으로 표시하며 접근은 허용하지 않는다.
- **예외 흐름:** 문서상 이름 변경 전의 공개 주소로 접근하면 시스템은 별도 이동 처리 없이 404로 응답한다.
- **결과:** 뷰어는 공개 문서의 현재 공개본만 읽는다.
- **관련 데이터:** 공개 문서 리비전, 공개 검색 대상, 활성 태그, 관계·위키링크 대상 상태

### UC-25. 관리자 권한 변경 이력을 확인한다

- **관련 사용자 스토리:** US-11
- **행위자:** 운영자 또는 해당 월드 관리자
- **목적:** 부관리자 초대·권한 변경·소속 해제의 결과를 추적한다.
- **기본 흐름:** 행위자가 자신이 볼 수 있는 월드의 관리자 이력을 확인한다. 시스템은 수행자, 대상 계정, 관련 초대와 변경 전후 상태를 보여 준다.
- **예외 흐름:** 부관리자는 관리자 이력을 볼 수 없다.
- **결과:** 권한 변경의 근거와 결과를 검토할 수 있다.
- **관련 데이터:** 관리자 감사 이력, 역할, 세부 허가, 초대
