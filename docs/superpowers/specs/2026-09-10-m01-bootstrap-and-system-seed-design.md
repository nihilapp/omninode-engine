# M01 최초 운영자·시스템 카탈로그 초기화 설계

> 분류: M01 제품 스키마 구현 설계
>
> 상태: 마스터 위임에 따른 기술 결정 확정
>
> 근거: `2026-08-29-omninode-requirements-decisions.md`, `2026-08-29-omninode-data-schema.md`, `2026-08-29-omninode-user-story-data-flow.md`, `2026-08-30-omninode-validation-rules.md`, `2026-08-30-omninode-state-transitions.md`, `2026-09-10-m01-default-data-source-design.md`
>
> 범위: 최초 운영자 한 건의 감사 컬럼 예외, 시스템 기본 카탈로그의 최초 적재·재실행·실패 처리 절차를 확정한다. 실제 환경 변수 파일, 스크립트, ORM 코드, JSON 스냅샷, 마이그레이션, 이메일 발송은 포함하지 않는다.

## 목표와 확정 전제

1. 일반 회원 가입은 없으며, 최초 설치 때 실제 로그인 가능한 운영자 계정 한 건을 직접 만든다. 시스템용 가상 계정은 만들지 않는다.
2. 최초 운영자 `admins` 행만 최초 생성 때 `creatr_id`를 비울 수 있다. 그 뒤 생성하는 역할·허가·시스템 카탈로그를 포함한 모든 행은 이 운영자의 ID를 `creatr_id`로 기록한다.
3. 최초 운영자는 전역 운영자 역할, 전역 범위의 24개 허가 모두 `Y`, 임시 비밀번호 변경 필요 상태를 가진다.
4. 시스템 기본 카탈로그는 공통 카테고리 97개, 관계 유형 936개와 대상 역할 2,813개, 공통 템플릿 11종을 현재 저장소의 버전 관리 스냅샷으로 적재한다. 실제 월드·프로젝트·문서는 만들지 않는다.
5. 최초 초기화는 중간 상태를 남기지 않는 하나의 DB 트랜잭션으로 처리한다. 같은 스냅샷의 시스템 카탈로그 적재는 재실행해도 중복이나 조용한 덮어쓰기를 만들지 않는다.
6. 초기 비밀번호·DB 연결 문자열·접근 비밀값은 명령 인자, 콘솔 출력, 로그, 저장소에 기록하지 않는다.

## 실행 단위와 순서

```text
1. Prisma 마이그레이션 적용
2. 명시적 bootstrap 명령
   ├─ 최초 운영자 생성
   ├─ 전역 운영자 역할·24개 허가 생성
   └─ 시스템 카탈로그 1차 적재
3. 이후 명시적 system-seed 명령
   └─ 같은 카탈로그 재검증 또는 새 카탈로그 버전의 추가 적재
```

마이그레이션 적용, bootstrap, system-seed는 모두 명시적인 운영 명령으로 둔다. `postinstall`, 개발 서버 시작, 빌드, `prisma migrate deploy` 자체에서 자동 실행하지 않는다. 운영 DB에 빈 구조만 배포되거나, 의도하지 않은 계정·기본 데이터가 생기는 일을 막기 위해서다.

### 명령의 책임

| 명령 | 실행 조건 | 성공 결과 | 재실행 결과 |
| --- | --- | --- | --- |
| `db:bootstrap` | 최신 마이그레이션 적용 뒤, 등록된 초기 운영자와 시스템 카탈로그가 모두 없는 DB | 최초 운영자·전역 역할·전역 24개 허가·현재 시스템 카탈로그를 하나의 트랜잭션으로 생성 | 같은 초기 운영자와 동일 카탈로그가 이미 완성돼 있으면 변경 없이 성공한다. 하나만 있거나 내용이 달라진 불완전 상태면 실패한다. |
| `db:seed:system` | 최신 마이그레이션 적용 뒤, 명시한 활성 운영자 계정이 존재 | 현재 스냅샷에 없는 시스템 정의만 추가하고, 기존 정의는 동등성 검증 | 같은 스냅샷이면 변경 없이 성공한다. 같은 불변 코드의 내용이 스냅샷과 다르면 실패하며 기존 행을 덮어쓰지 않는다. |

두 명령은 시작 전에 DB 전역 초기화 잠금을 얻는다. 따라서 서로 다른 배포 작업이나 운영자가 동시에 실행해도 최초 운영자 또는 시스템 카탈로그를 중복 생성하지 않는다.

## 최초 운영자

### 필수 운영 입력

M02에서 bootstrap 명령은 아래 환경 변수만 읽는다. 실제 변수명은 이 설계의 이름을 따르며, 값은 `.env.*.example`에 비밀값 없이 키만 문서화한다.

| 환경 변수 | 용도 | 출력·저장 원칙 |
| --- | --- | --- |
| `BOOTSTRAP_OPERATOR_EMAIL` | 최초 운영자의 로그인 이메일 | 로그에는 마스킹한 결과만 남긴다. |
| `BOOTSTRAP_OPERATOR_DISPLAY_NAME` | 최초 운영자의 표시 이름 | 일반 데이터로 저장한다. |
| `BOOTSTRAP_OPERATOR_PASSWORD` | 최초 로그인에 쓸 임시 비밀번호 | Argon2id PHC 해시만 저장하며 원문은 로그·출력·DB에 남기지 않는다. |
| `SYSTEM_SEED_ACTOR_EMAIL` | 재실행 system-seed의 감사 수행자 식별 | 활성 전역 운영자와 일치해야 한다. 비밀값이 아니다. |

초기 비밀번호는 공백을 제외한 ASCII 문자 8자 이상 128자 이하이고, 숫자·영문 소문자·영문 대문자·특수문자를 각각 하나 이상 포함해야 한다. bootstrap은 비밀번호를 새로 생성하거나 출력하지 않는다. 설치자가 안전한 배포 비밀값으로 직접 제공하고, 최초 로그인 뒤 비밀번호 변경 기능에서 바꾼다.

### 최초 운영자 트랜잭션

1. DB 전역 초기화 잠금을 얻고 마이그레이션 적용 상태와 필수 환경 변수를 확인한다.
2. `admins`와 시스템 카탈로그 대상 테이블의 상태를 확인한다. 둘 다 비어 있을 때만 최초 생성 흐름으로 들어간다.
3. UUID v7을 만든 뒤 최초 운영자 `admins` 행을 `use_yn='Y'`, `del_yn='N'`, `tmpr_pswd_yn='Y'`, `creatr_id=NULL`로 한 번 생성한다. 이 행 이외의 bootstrap 생성 행에는 같은 UUID를 `creatr_id`로 넣는다.
4. 월드·프로젝트 범위가 비어 있는 전역 운영자 `admin_roles` 행과, 24개 허가가 모두 `Y`인 전역 `admin_prmsn_ruls` 행을 만든다.
5. 같은 트랜잭션 안에서 시스템 카탈로그 적재기를 호출한다.
6. 시스템 카탈로그의 수량·코드·참조·템플릿 최초 리비전이 모두 검증되면 커밋한다. 하나라도 실패하면 최초 운영자와 그 뒤 행까지 전부 롤백한다.

`creatr_id`는 계정 완전 삭제 뒤 과거 참조를 보존하기 위해 나중에 `NULL`이 될 수 있다. 이 설계의 예외는 **초기 생성 시점**에만 적용한다. 따라서 최초 운영자 생성 이후의 행은 생성 시 실제 수행자 ID를 반드시 기록하고, 탈퇴에 따른 `SET NULL` 이력 보존을 위반으로 처리하지 않는다.

최초 운영자는 임시 비밀번호 상태이므로, M03 인증 구현 전까지는 관리 API나 페이지에 접근할 수 없고 비밀번호 변경 흐름만 허용한다. bootstrap은 이메일을 보내지 않는다. 설치자가 직접 입력한 비밀번호를 사용하는 초기 설치 절차이므로, 일반 관리자 생성·초대에서의 임시 비밀번호 이메일 발송과 다른 경로다.

## 시스템 카탈로그 적재

### 적재 범위와 순서

시스템 카탈로그 적재기는 [시스템 기본 데이터 출처·적재 설계](./2026-09-10-m01-default-data-source-design.md)와 [시스템 기본 템플릿 카탈로그](../../project-design/2026-09-10-omninode-system-template-catalog.md)의 동결 입력을 저장소 내부 JSON 스냅샷으로 바꾼 뒤 사용한다.

1. 시스템 기본 카테고리 97개를 상위 카테고리부터 적재한다.
2. 시스템 기본 관계 유형 936개를 적재한다.
3. 관계 유형별 대상 역할 2,813개와 역할별 허용 카테고리 연결을 적재한다.
4. 시스템 기본 템플릿 11종, 영속 섹션, 최초 템플릿 리비전과 리비전 섹션 스냅샷을 적재한다.
5. 템플릿 스냅샷 안에 메인 카테고리 코드와 기본 템플릿 코드를 함께 보존한다. 프로젝트 생성 기능은 나중에 이 매핑을 이용해 `prj_ctgrys`와 `prj_tmplts`의 프로젝트별 기본 연결을 만든다.

적재는 `worlds`, `prjs`, `docs`, `prj_ctgrys`, `prj_tmplts`, 실제 관계 인스턴스를 만들지 않는다. 프로젝트 위그드라실·룩스테라·엘드로스의 월드·프로젝트·문서·확장 카테고리·이관 템플릿도 만들지 않는다.

### 재실행과 버전 충돌

시스템 정의의 불변 코드가 재실행 판정의 기준이다. 카테고리·템플릿·관계 유형과 영속 섹션의 코드, 역할 코드, 역할-카테고리 연결을 스냅샷과 비교한다.

| 상황 | 처리 |
| --- | --- |
| 스냅샷에만 있는 불변 코드 | 현재 수행자 `creatr_id`로 새 시스템 정의를 추가한다. |
| DB와 스냅샷의 동일 코드·동일 내용 | 변경하지 않고 통과한다. |
| 동일 코드인데 이름·순서·구조·참조가 다름 | 실패한다. 기존 시스템 정의를 갱신·삭제·재정렬하지 않는다. |
| DB에만 있는 시스템 코드 | 실패한다. 현재 스냅샷보다 다른 카탈로그가 적용된 것이므로 명시적 카탈로그 변경 작업을 먼저 검토한다. |

이 방식은 같은 카탈로그의 반복 실행을 안전하게 하면서도, 동결 정본의 변경을 무심코 운영 데이터에 덮어쓰지 않게 한다. 새 시스템 카탈로그 버전은 새 JSON 스냅샷, 입력 해시·수량 검증, 변경 설계와 마이그레이션 검토를 거쳐 별도 작업으로 반입한다.

## 실패와 복구

1. 필수 환경 변수가 비어 있거나 비밀번호 규칙을 통과하지 않으면 DB 쓰기 전 실패한다.
2. 마이그레이션이 최신이 아니거나 필수 테이블·제약이 없으면 DB 쓰기 전 실패한다.
3. 최초 운영자만 있거나 시스템 카탈로그만 있는 불완전 DB는 bootstrap이 수정하지 않고 실패한다. 운영자는 원인을 확인한 뒤 `db:seed:system`으로 설계된 복구 절차를 실행하거나 테스트 DB를 새로 만든다.
4. 카탈로그의 수량·해시·코드·참조·최초 리비전 검증 중 하나라도 실패하면 해당 명령의 트랜잭션을 전부 롤백한다.
5. 오류와 성공 로그에는 명령 결과, 카탈로그 버전, 항목별 수량, 마스킹한 이메일만 기록한다. 비밀번호 원문·해시 전체·접근 비밀값·DB 연결 문자열은 기록하지 않는다.
6. bootstrap과 system-seed는 서버 요청 경로나 공개 API에서 호출하지 않는다. 권한 있는 배포 운영자가 직접 실행하는 로컬·CI 운영 명령으로만 둔다.

## M02 검증 기준

| 검증 영역 | 통과 기준 |
| --- | --- |
| 최초 설치 | 빈 테스트 DB에서 운영자 1명, 전역 운영자 역할 1건, 전역 24개 `Y` 허가 1건, 시스템 카탈로그가 한 트랜잭션으로 생성된다. |
| 감사 컬럼 | 최초 운영자 생성 시에만 `creatr_id`가 비고, 역할·허가·카탈로그의 생성자 ID는 최초 운영자 ID와 같다. |
| 임시 비밀번호 | 원문은 저장·출력·로그에 없고 Argon2id PHC 해시만 있으며, `tmpr_pswd_yn='Y'`다. |
| 기본 데이터 | 카테고리 97개, 관계 유형 936개, 대상 역할 2,813개, 공통 템플릿 11종의 수량·코드·부모·역할·섹션·최초 리비전·참조가 스냅샷과 일치한다. |
| 재실행 | 같은 bootstrap·system-seed 실행은 행 수·감사 값·참조를 바꾸지 않는다. |
| 충돌 | 부분 적재, 다른 코드 집합, 같은 코드의 다른 내용은 실패하고 기존 데이터를 변경하지 않는다. |
| 범위 분리 | bootstrap 뒤 실제 월드·프로젝트·문서·룩스테라·엘드로스 데이터가 없고, 프로젝트 생성 전 `prj_ctgrys`·`prj_tmplts` 행도 없다. |
| 격리 | `TEST_DATABASE_URL`의 DB 이름이 `_test`로 끝나지 않으면 파괴적 초기화·통합 테스트를 거부한다. |

## 범위 밖 항목

- 실제 `package.json` 명령, 환경 변수 예시 파일, JSON 스냅샷, Argon2id 라이브러리 호출, 트랜잭션 코드, 마이그레이션과 테스트 구현은 M02 구현 계획·승인 뒤에 작성한다.
- 일반 관리자 생성, 부관리자 초대, 이메일 전송, 최초 비밀번호 변경 화면과 인증 API는 M03 이후의 인증·권한 구현 범위다.
- 새로운 시스템 카탈로그 버전의 내용 결정, 기존 시스템 정의 변경·삭제·재정렬, 실제 세계관 이관은 별도 제품·이관 작업으로 둔다.
