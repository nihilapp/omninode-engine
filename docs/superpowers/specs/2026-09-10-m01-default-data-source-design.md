# M01 시스템 기본 데이터 출처·적재 설계

> 분류: M01 제품 스키마 구현 설계
>
> 상태: 확정
>
> 근거: `2026-08-29-omninode-data-schema.md`, `2026-09-04-omninode-development-roadmap.md`, 프로젝트 위그드라실의 데이터베이스 이관 사전 작업 동결본
>
> 범위: 시스템 기본 관계 유형·카테고리·템플릿의 콘텐츠 정본 위치, 저장소 반입 방식, 초기 적재 순서와 검증 기준을 정한다. 실제 데이터 파일, ORM 코드, 시드 명령, 마이그레이션은 포함하지 않는다.

## 결정 요약

1. 시스템 기본 관계 유형은 프로젝트 위그드라실의 **범용 관계 유형 v1 동결본**을 사용한다. COMMON 관계 유형 936개, 대상 역할 2,813개와 역할별 허용 카테고리 매핑이 모두 이 범위의 정본이다.
2. 시스템 기본 카테고리는 같은 설정 저장소의 **카테고리 이관 데이터 v1 동결본**을 사용한다. 공통 11개 메인 카테고리와 86개 하위 카테고리, 합계 97개를 시스템 기본 정의로 사용한다.
3. 룩스테라 `용종` 17개와 엘드로스 `클래스` 3개는 특정 세계관의 확장 데이터다. 시스템 기본 데이터에는 넣지 않고, 해당 세계관을 이관할 때만 별도 프로젝트 데이터로 적재한다.
4. 현재 Omninode 스키마에서는 과거 PostgreSQL·SQLite 시드 SQL을 실행하지 않는다. 그 SQL은 값·수량·순서의 검증 근거로만 사용하며, 실제 적재는 현재 스키마에 맞춘 버전 관리 JSON 스냅샷과 명시적 재실행 가능 시드 명령으로 구현한다.
5. 시스템 기본 템플릿은 이미 확정된 공통 11종을 사용한다. 룩스테라·엘드로스의 현재 템플릿 파일은 이 공통 정본을 대체하지 않는 세계관별 프로젝트 사용자 정의 또는 이관 템플릿이다.

## 콘텐츠 정본

| 대상 | 정본 | 수량·판정 | 반입 시 우선 규칙 |
| --- | --- | --- | --- |
| COMMON 관계 유형 | `프로젝트 위그드라실/설정 정비/데이터베이스 이관 사전 작업/범용 관계 유형/2.1`부터 `2.15` 확정본 | 936개, 전역 ID 1~936 연속 | `검토 및 추적/범용 관계 유형 v1 최종 검토 및 동결.md`의 관계명·역방향명·역할명 정정을 최종 오버레이로 적용한다. |
| 관계 역할·허용 카테고리 | 같은 폴더의 `2.1~2.10`부터 `2.15 관계 대상 카테고리 매핑.md`, 세계별 확장 매핑, 적용 규칙 | 역할 2,813개, 전수 검증 완료 | 범용 11개 메인 카테고리 기준으로 읽는다. 하위 카테고리는 해당 메인 카테고리 허용 범위에 포함한다. |
| 시스템 기본 카테고리 | `검토 및 추적/카테고리 이관 데이터 v1 최종 검토 및 동결.md`와 `카테고리 및 분류 체계/카테고리 및 서브카테고리 이관 정리.md` | 메인 11개 + 하위 86개 = 97개, 초기 깊이 2 | 전체 이름·부모 경로·순서를 그대로 사용한다. 빈 분류, `일반`, 빈값, `기타` 노드는 만들지 않는다. |
| 세계관 확장 카테고리 | 같은 카테고리 동결본의 룩스테라 용종 17개·엘드로스 클래스 3개 | 각각 특정 세계관 전용 | 시스템 기본 카탈로그와 분리한 프로젝트 이관 입력으로 둔다. |
| 시스템 기본 템플릿 | [시스템 기본 템플릿 카탈로그](../../project-design/2026-09-10-omninode-system-template-catalog.md) | 공통 11종 | 공통 11개 메인 카테고리에 하나씩 기본 연결한다. 세계관별 개별 양식은 이 카탈로그를 덮어쓰지 않는다. |

관계 문장 결합 템플릿은 관계 유형·역할·허용 카테고리의 초기 적재를 막지 않는다. 다만 이전 검토에서 관계별 문장 서식 매핑 278개만 확정되고 658개가 남아 있었으므로, 문장 생성 기능을 설계·구현하기 전에 별도로 처리한다. 이를 관계 유형 자체의 936개 동결 또는 역할별 허용 카테고리 매핑 미결과 혼동하지 않는다.

## 저장소 반입과 적재 경계

```text
프로젝트 위그드라실 동결 정본
  → 검증 가능한 변환
  → omninode-engine 내부의 버전 관리 JSON 스냅샷
  → 명시적이고 재실행 가능한 시스템 카탈로그 시드
  → 프로젝트·월드 생성 시 참조 행 생성
```

1. M02 구현 전에 동결 정본을 현재 저장소 안의 시스템 카탈로그 JSON으로 변환해 함께 버전 관리한다. 운영 배포의 시드는 외부 설정 폴더를 직접 읽지 않는다.
2. 변환 입력에는 동결 문서의 SHA-256과 수량을 기록한다. 값이 바뀌거나 수량이 달라지면 새 카탈로그 버전을 만들며, 기존 카탈로그를 조용히 덮어쓰지 않는다.
3. 시스템 카탈로그 시드는 같은 버전을 여러 번 실행해도 중복 정의를 만들지 않아야 한다. 시스템 기본 카테고리와 관계 유형은 한 번 정의하고, 각 프로젝트·월드는 그 정의를 복제하지 않고 참조한다.
4. 실제 세계관 프로젝트·월드·문서의 이관은 시스템 카탈로그 적재와 분리한다. 따라서 일반 Omninode 설치가 프로젝트 위그드라실, 룩스테라, 엘드로스나 세계관 확장 카테고리를 자동 생성하지 않는다.
5. 모든 시스템 카탈로그 행은 공통 감사 컬럼을 가지므로, 최초 운영자 생성 절차와 생성자 기록 규칙은 M01의 `최초 운영자` 결정 뒤 같은 실행 단위에서 연결한다.

과거 `초기 프로젝트·월드·카테고리 시드.postgresql.sql`과 SQLite 파일은 동결 당시 214개 카테고리의 수량·순서 검증에는 유용하지만, 기존 물리 테이블과 ID 전략을 전제로 한다. 현재 `ctgrys`, `prj_ctgrys`, `rel_types` 등 Omninode 설계에 그대로 실행하거나 변환 없이 재사용하지 않는다.

## 초기 적재 순서와 검증 기준

1. M01의 최초 운영자·감사 컬럼 초기화 규칙을 확정한다.
2. 시스템 기본 카테고리 97개를 메인 카테고리부터 하위 카테고리 순으로 적재한다.
3. COMMON 관계 유형 936개를 동결 전역 ID와 최종 명칭으로 적재한다.
4. 대상 역할 2,813개와 범용 메인 카테고리 기준 허용 매핑을 적재한다.
5. 공통 시스템 기본 템플릿 11종과 최초 리비전·섹션을 적재하고, 메인 카테고리의 기본 템플릿 연결을 만든다.
6. 특정 세계관을 이관할 때에만 해당 확장 카테고리·SERIES 관계·실제 월드별 사용 참조를 별도 입력으로 적재한다.

검증은 최소한 다음을 확인한다.

| 검증 대상 | 통과 기준 |
| --- | --- |
| 관계 유형 | COMMON 936개, 전역 ID 1~936의 중복·누락 0건, 동결 정정 명칭 반영 |
| 대상 역할 | 2,813개, 같은 관계 유형 안의 역할명 중복 0건, 역할 순서·필수 여부 보존 |
| 시스템 카테고리 | 97개, 메인 11개·하위 86개, 최대 깊이 2, 빈·일반·기타 노드 0건 |
| 시스템 기본 템플릿 | 공통 11종, 각 메인 카테고리의 기본 연결 1건, 첫 필수 섹션 `개요`와 마지막 고정 섹션 `요약` 일치 |
| 세계관 확장 분리 | 기본 카탈로그에 용종·클래스 확장과 프로젝트 위그드라실·룩스테라·엘드로스 행이 없음 |
| 재실행 | 같은 카탈로그 버전의 반복 적재가 중복 행이나 참조 변경을 만들지 않음 |
| 정본 추적 | 입력 문서 경로·해시·수량과 저장소 스냅샷 메타데이터가 일치 |

## 시스템 기본 템플릿 적용

시스템 기본 템플릿의 공통 정본과 11개 메인 카테고리 연결은 [시스템 기본 템플릿 카탈로그](../../project-design/2026-09-10-omninode-system-template-catalog.md)를 따른다. 현재 제품의 템플릿 연결은 대분류에만 둘 수 있으므로, 지형 하위 유형인 대륙의 전문 구조는 시스템 기본 11종의 자동 연결에 넣지 않는다. 프로젝트가 그 구조를 사용하려면 프로젝트 사용자 정의 템플릿으로 만든다.
