# M01 로그인 세션 저장·검증 설계

>
> 근거: `2026-08-29-omninode-requirements-decisions.md`, `2026-08-29-omninode-data-schema.md`, `2026-08-30-omninode-validation-rules.md`, `2026-08-30-omninode-failure-conditions.md`, `2026-08-30-omninode-state-transitions.md`, `2026-09-03-omninode-route-api-design.md`
>
> 범위: 로그인 세션의 저장 구조, 유효성 판정, 전역 종료와 구현 제약을 확정한다. ORM 코드, 마이그레이션, API 핸들러, 쿠키 코드, 테스트 구현은 포함하지 않는다.

## 목표와 확정 전제

1. 로그인 성공 시 접근 자격증명은 최대 1시간 동안만 유효하다.
2. 리프레시 자격증명의 전체 유효 기간은 로그인 성공 시점부터 고정 7일이다.
3. 접근 자격증명 재발급과 1분 주기의 세션 점검은 7일 만료 시각을 연장하지 않는다.
4. 여러 기기·브라우저가 동시에 로그인할 수 있다. 그러나 계정의 전역 로그인 유효 기간, 만료, 로그아웃, 탈퇴 차단과 강제 접근 차단은 모두 함께 적용한다.
5. 브라우저가 서로 리프레시 비밀값을 공유하지 않고, 서버는 비밀값 원문을 저장하거나 API 응답·로그에 노출하지 않는다.
6. 세션 점검은 마지막 접속 시각을 기록하기 위한 1분 주기 흐름이다. 접근 차단은 이 점검을 기다리지 않고 모든 인증 요청에서 즉시 판정한다.

## 결정한 구조

로그인 상태는 하나의 전역 세션과 여러 브라우저별 자격증명으로 나눈다.

```text
관리자 계정 1건
  └─ 전역 로그인 세션 0..1건 (유효 상태)
       └─ 브라우저별 리프레시 자격증명 1..N건
```

| 구성 | 책임 | 보관하지 않는 정보 |
| --- | --- | --- |
| `admin_ssns` | 계정별 전역 로그인 시작 시각, 고정 만료 시각, 마지막 접속 시각, 유효·만료·종료 상태 | 접근 토큰 원문, 브라우저별 리프레시 비밀값 원문 |
| `admin_ssn_clnts` | 로그인한 브라우저별 리프레시 비밀값의 검증용 해시 | 브라우저 이름·기기 지문·IP 주소·비밀값 원문 |
| 접근 자격증명 | 서명, 계정·전역 세션·브라우저 자격증명 연결 식별자, 만료 시각으로 짧은 접근을 증명 | 데이터베이스 영구 저장 |

이 구조에서 사용자가 체감하는 로그인 유효 기간은 계정당 하나다. 브라우저마다 별도의 리프레시 비밀값을 둔 이유는 쿠키를 브라우저 사이에 공유하지 않으면서도, 상위 전역 세션 하나를 끝내 모든 브라우저를 즉시 차단하기 위해서다.

## 저장 모델과 참조 규칙

### 전역 로그인 세션 `admin_ssns`

| 항목 | 결정 |
| --- | --- |
| 식별 | UUID v7 `id` |
| 소유 | `admin_id`가 `admins.id`를 참조 |
| 시간 | `lgn_dt`, 고정 `expry_dt`, 1분 점검으로만 갱신하는 `last_cntn_dt` |
| 상태 | 논리 상태 유효·만료·종료를 `ssn_stt_cd`에 기록 |
| 활성 중복 | `del_yn = 'N'`이고 유효 상태인 행은 `admin_id`당 최대 하나 |
| 종료 | 전역 로그아웃, 탈퇴 확정, 강제 접근 차단은 유효 행을 종료로 전환 |
| 계정 삭제 | 계정 완전 삭제 때 이력 보존 대상이 아니므로 하위 브라우저 자격증명과 함께 완전 삭제 |

유효 세션은 상태값만이 아니라 `expry_dt`까지 함께 확인해야 한다. 만료 시각이 지났지만 아직 정리 작업이 세션 상태를 만료로 바꾸지 않은 경우에도 유효하지 않다. 로그인·리프레시·세션 점검·보호 요청이 이를 처음 확인한 서비스 트랜잭션에서 만료 상태를 기록한다. 새 로그인은 해당 만료 처리를 끝낸 뒤에만 새 전역 세션을 만든다.

### 브라우저별 리프레시 자격증명 `admin_ssn_clnts`

| 항목 | 결정 |
| --- | --- |
| 식별 | UUID v7 `id` |
| 소유 | `admin_ssn_id`가 `admin_ssns.id`를 참조 |
| 비밀값 | 고엔트로피 리프레시 비밀값의 `resh_tkn_hash`만 저장 |
| 유효 기간·상태 | 독자 컬럼을 두지 않고 상위 전역 세션의 만료·상태를 상속 |
| 생성 | 브라우저에서 로그인에 성공할 때마다 한 행 생성 |
| 전역 종료 | 상위 세션이 만료·종료되면 모든 하위 행의 리프레시를 즉시 거부 |
| 계정 삭제 | 상위 전역 세션 삭제와 함께 완전 삭제 |

브라우저 쿠키에는 브라우저별 자격증명 식별자와 고엔트로피 비밀값을 함께 담는다. 서버는 식별자로 행 하나를 찾은 뒤 비밀값의 해시를 비교한다. 비밀값은 `HttpOnly` 쿠키로만 전달하며, 프런트엔드 JavaScript와 API 응답·로그에는 제공하지 않는다. 해시 방식과 서명 알고리즘의 라이브러리·매개변수는 M03 구현 계획에서 선택하되, 저장된 해시만으로 자격증명을 재현할 수 없어야 한다.

## 자격증명 발급·검증 흐름

### 로그인

1. 계정의 로그인 정보와 일반 서비스 접근 가능 상태를 확인한다.
2. 해당 계정의 유효 전역 세션을 잠금 상태로 확인한다.
3. 유효 세션이 없으면 `lgn_dt`와 `last_cntn_dt`를 현재 시각, `expry_dt`를 정확히 7일 뒤로 한 전역 세션을 만든다. 만료된 유효 표기 세션이 있으면 먼저 만료로 전환한다.
4. 유효 세션이 있으면 그 세션을 그대로 사용한다. 이때 `expry_dt`와 `lgn_dt`를 바꾸지 않는다.
5. 로그인한 브라우저의 리프레시 비밀값 해시 행을 만들고, 접근 자격증명과 리프레시 자격증명을 각각 `HttpOnly` 쿠키로 발급한다.

동시에 여러 브라우저에서 로그인해도 전역 세션을 둘 이상 만들지 않는다. 활성 전역 세션 고유 제약과 트랜잭션 잠금은 이 경쟁 상태를 막으며, 각 브라우저에는 서로 다른 하위 자격증명 행만 추가된다.

### 보호 요청과 접근 자격증명 재발급

1. 보호 요청은 먼저 접근 자격증명의 서명·만료를 검사한다.
2. 서버는 자격증명에 연결된 전역 세션과 브라우저별 자격증명 행을 조회해, 삭제·사용 중지 상태, 전역 세션 논리 상태, 전역 만료 시각, 계정의 일반 서비스 접근 가능 상태를 모두 확인한다.
3. 보호 요청은 현재 역할·월드·프로젝트 범위·세부 허가도 매번 다시 판정한다.
4. 접근 자격증명이 만료됐을 때 리프레시 요청은 같은 전역 세션과 브라우저별 자격증명 검증을 통과한 경우에만 새 접근 자격증명을 발급한다.
5. 새 접근 자격증명의 만료 시각은 `현재 시각 + 1시간`과 전역 세션 `expry_dt` 중 이른 시각을 넘을 수 없다.

따라서 7일 만료 시각 직전의 재발급은 1시간보다 짧은 접근 자격증명을 만들 수 있다. 이는 모든 브라우저의 전역 만료를 같은 시점에 강제하기 위한 직접적인 결과다.

### 1분 세션 점검과 전역 종료

1. 로그인 상태의 클라이언트는 1분마다 현재 세션 확인을 요청한다.
2. 성공한 확인만 `admin_ssns.last_cntn_dt`를 현재 시각으로 갱신한다. 이 갱신은 `lgn_dt`, `expry_dt`, `ssn_stt_cd`를 바꾸지 않는다.
3. 점검 실패 뒤에는 즉시 반복 요청하지 않는다. 다음 정규 1분 점검 또는 사용자의 명시적 동작에서만 다시 확인한다.
4. 전역 로그아웃, 탈퇴 확정, 강제 접근 차단은 전역 세션을 종료한다. 다음 보호 요청·세션 점검·리프레시에서 상위 세션 상태가 다시 확인되므로 모든 브라우저가 함께 일반 서비스에서 나간다.

1분 점검은 마지막 접속 기록과 화면 상태를 위한 보조 흐름이다. 요청마다 수행하는 전역 세션 검증이 실제 접근 제어의 기준이므로, 점검 주기 사이에도 전역 종료는 즉시 적용된다.

## 쿠키와 요청 보호 기준

1. 접근 자격증명과 리프레시 자격증명은 모두 `HttpOnly` 쿠키만 사용한다.
2. 운영 환경 쿠키에는 `Secure`와 적절한 `SameSite` 속성을 적용한다.
3. 상태를 바꾸는 인증·관리 요청은 서버의 출처 검증을 통과해야 한다.
4. 자격증명 원문은 URL, 응답 본문, 클라이언트 상태 저장소, 서버 로그에 남기지 않는다.
5. 유효하지 않은 접근·리프레시 자격증명을 발견하면 해당 응답에서 현재 브라우저의 쿠키를 제거한다. 다른 브라우저의 하위 자격증명은 전역 세션이 유효한 한 영향을 받지 않는다.

## DB 구현 제약 분리

| 범위 | 구현해야 할 제약 |
| --- | --- |
| ORM 선언 | 두 테이블의 UUID v7 키, 계정·상위 세션 참조, 공통 8개 감사 컬럼, 필수 시간·상태·해시 컬럼, 상위 삭제에 따른 하위 완전 삭제 관계 |
| DB 전용 마이그레이션 | 활성·미삭제 전역 세션의 계정별 부분 고유 제약, 리프레시 해시 고유 제약, `expry_dt`가 `lgn_dt`보다 뒤라는 시간 정합성, 공통 `use_yn`·`del_yn`의 허용값 제약 |
| 서비스 트랜잭션 | 만료 상태 전환 뒤 새 전역 세션 생성, 동시에 로그인할 때 기존 유효 세션 재사용, 전역 종료의 원자적 반영, 리프레시 해시 비교와 새 접근 자격증명 발급 |

시간에 따라 달라지는 유효 여부를 DB 인덱스 조건에 직접 넣지 않는다. 대신 유효 상태 행의 계정별 부분 고유 제약을 두고, 로그인 트랜잭션이 만료 시각을 확인해 먼저 상태를 만료로 바꾼다. PostgreSQL의 부분 인덱스 조건은 현재 시각처럼 변하는 값을 안전한 고유 기준으로 사용할 수 없기 때문이다.

## 구현 전 검증 기준

1. 첫 로그인은 전역 세션 하나, 브라우저별 자격증명 하나, 정확히 7일 뒤 전역 만료 시각을 만든다.
2. 유효 기간 중 다른 브라우저 로그인은 같은 전역 세션을 사용하고, 만료 시각을 바꾸지 않으며, 새 브라우저별 자격증명만 만든다.
3. 리프레시 재발급은 접근 자격증명을 최대 1시간 발급하되 전역 만료 시각을 넘기지 않는다.
4. 전역 만료·전역 로그아웃·탈퇴 확정·강제 접근 차단은 모든 브라우저의 보호 요청과 리프레시를 즉시 거부한다.
5. 리프레시 비밀값이 일치하지 않거나 상위 세션이 유효하지 않으면 접근 자격증명과 마지막 접속 시각을 바꾸지 않는다.
6. 1분 세션 점검만 마지막 접속 시각을 바꾸며, 접근 자격증명 재발급과 일반 요청은 전역 만료 시각을 연장하지 않는다.
7. 동시 로그인에서도 계정당 유효 전역 세션이 둘 이상 생기지 않는다.
8. 쿠키·응답·로그에 접근 자격증명 또는 리프레시 비밀값 원문이 남지 않고, 상태 변경 요청은 출처 검증을 통과해야 한다.

## 범위 밖 항목

- Prisma 모델, SQL 마이그레이션, 쿠키 이름·경로·도메인, 서명·해시 라이브러리와 매개변수, API 핸들러, 인증 미들웨어, 프런트엔드 1분 타이머는 M02·M03 구현 계획에서 다룬다.
- 기기별 이름 표시, 기기별 로그아웃, 로그인 이력 열람, IP·지문 기반 이상 로그인 탐지는 현재 제품 범위에 없다.
- 세션 이력의 보관 기간과 정리 작업은 현재 제품 결정에 포함하지 않는다. 구현 시 이력 보관 요구가 생기면 별도 데이터 보존 결정을 먼저 받는다.
