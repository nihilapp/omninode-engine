# 바이브코딩 절차 기록

> 분류: 작업 설계
>
> 목적: 마스터가 제공한 기초 기획을 문답으로 1차 기획으로 구체화하고, 이를 사용자 스토리·유스케이스·데이터 플로우·데이터 스키마, 4차 기획, 프론트 라우트·API 설계로 전환하는 실제 절차를 보존한다. 이 문서는 나중에 에이전트 지침으로 옮길 기준 원본이다.

## 적용 범위

- 이 문서는 기초 기획 구체화, 사용자 스토리 목록화, 유스케이스 구체화, 데이터 플로우 구체화, 데이터 스키마 구상, 4차 기획과 그 뒤의 프론트 라우트·API 설계를 다룬다.
- 화면·상호작용 설계, API, ORM·마이그레이션·데이터베이스 변경은 4차 기획을 확정하기 전까지 다루지 않는다.
- 라우트·API 구현, ORM·마이그레이션·데이터베이스 변경은 별도 구현 승인이 있을 때만 다룬다.

## 기초 기획의 1차 기획화

마스터가 서비스·앱의 기초 기획을 제공하고 에이전트를 통한 구체화를 요청하면, 에이전트는 문답으로 이를 1차 기획으로 정리한다.

- 지정한 참고 폴더·문서를 먼저 확인한다.
- 한 번에 하나의 결정 단위만 묻고, 필요하면 이해하기 쉬운 선택지를 제공한다.
- 이미 확정한 결정의 직접적인 결과는 재질문하지 않고 파생 규칙으로 정리한다.
- 마스터의 선택·정정은 즉시 프로젝트의 제품 설계 문서에 기록한다.
- 기획 진행 규칙과 보류 항목은 작업 설계 문서에 기록하고, 기록 뒤에는 문서 형식 검사를 수행한다.
- 미확정 항목은 확정으로 취급하지 않고 별도로 보류한다.
- 이 절차는 1차 기획을 만드는 과정이며, 구현 권한을 뜻하지 않는다.

## 기획 보강 단계와 점검 순서

기초 기획을 구체화하고 구현 경계를 설계하는 과정은 다음 다섯 단계로 구분한다.

1. **1차 기획화:** 마스터가 제공한 기초 기획을 문답으로 구체화하고, 확정 결정과 미결 결정을 제품 설계 문서에 기록한다.
2. **2차 보강:** 1차 기획을 근거로 사용자 스토리를 목록화하고, 사용자 스토리에서 유스케이스를 도출한 뒤 유스케이스를 근거로 데이터 플로우를 구체화한다.
3. **3차 보강:** 데이터 플로우를 근거로 데이터 스키마의 테이블·컬럼·제약을 구상한다.
4. **4차 기획:** 프론트 라우트와 API 엔드포인트를 설계하기 전에 도메인 책임, 권한 매트릭스, 검증 규칙, 실패 조건, 상태 정의 및 전이를 순서대로 확립한다.
5. **라우트·API 설계:** 확정된 제품 경계를 근거로 페이지 역할과 이동 구조, API 네임스페이스·리소스·상태 전이·공통 응답을 설계하고 유스케이스 추적성을 점검한다.

2차 보강의 내부 순서는 **사용자 스토리 → 유스케이스 → 데이터 플로우**로 한다. 각 단계는 바로 앞 단계에서 확정된 내용을 근거로 하며, 이후 단계의 내용을 미리 확정하지 않는다.

데이터 스키마의 테이블 간 참조·범위·삭제 처리·제약 점검은 **스키마 초안을 작성한 뒤, 3차 보강을 확정하기 전에** 수행하는 점검 게이트다. 이 점검을 3차 보강이 끝난 뒤의 별도 다음 단계나 4차 보강으로 두지 않는다. 3차 보강이 완료된 뒤에는 스키마 간 점검을 새 작업으로 다시 제안하지 않는다.

유스케이스가 사용자 스토리·데이터 플로우 뒤에 작성됐거나, 후행 단계에서 상위 단계의 누락이 의심되면 각 단계의 추적 관계와 확정 정책을 전수 점검한다. 발견한 항목이 확정 정책의 직접적인 문서 누락이면 즉시 정정하고, 새로운 비즈니스·기획 판단이 필요한 경우에만 마스터와 논의한다.

## 4차 기획: 도메인 책임·권한·검증·실패 조건·상태 전이

4차 기획은 3차 보강과 유스케이스 후행 작성 정합성 점검을 마친 뒤에 시작한다. 이 단계가 끝나기 전에는 프론트 라우트나 API 엔드포인트를 확정하지 않는다.

1. **도메인 책임 정의:** 각 도메인이 소유하는 개념·상태·행동·다른 도메인과의 경계를 정리한다. 화면·API·테이블 구현을 미리 정하지 않는다.
2. **권한 매트릭스:** 역할과 범위별로 조회·생성·수정·삭제·특수 행동의 허용 여부를 정리한다. 이미 정한 권한의 직접적인 결과는 재질문하지 않는다.
3. **검증 규칙:** 입력값, 범위, 상태 전이, 중복, 참조 정합성처럼 행동이 성공하기 위한 조건을 정리한다.
4. **실패 조건:** 권한 부족, 입력 오류, 상태 충돌, 삭제·비공개·비활성 대상 접근처럼 행동을 수행할 수 없는 경우와 시스템 결과를 정리한다.
5. **상태 정의 및 전이:** 각 도메인의 상태값, 최초 상태, 허용 전이, 전이 주체, 전이 결과와 전이 금지 조건을 정리한다.

각 하위 단계를 마칠 때마다 다음을 수행한다.

- 확정한 제품 규칙은 `docs/project-design/`에 즉시 기록한다.
- 진행 순서, 작성 기준, 점검 기준은 이 절차 문서와 프로젝트·사용자 에이전트 지침에 즉시 갱신한다.
- 확정 정책의 직접 결과는 기록만 하고 재질문하지 않는다. 새로운 비즈니스·기획 판단이 필요한 항목만 미결로 분리해 마스터에게 한 결정 단위로 묻는다.
- 문서 갱신 뒤 `git diff --check`와 공백 검사를 수행한다.

도메인 책임 정의 문서에는 최소한 도메인명, 소유 개념·상태, 책임 행동, 다른 도메인과의 경계, 횡단 정책의 소유자를 기록한다. 한 상태를 둘 이상의 도메인이 직접 변경하는 것으로 적지 않으며, 도메인 간 영향은 상태 전이 또는 참조 규칙으로 명확히 한다.

권한 매트릭스에는 역할별 기본 범위, 관리 대상·행동별 허용 여부, 24개 허가 묶음과 실제 행동의 연결, 특수 권한 규칙을 기록한다. 역할 이름과 세부 허가의 책임을 섞지 않으며, 문서 허가에 포함되는 부수 행동처럼 예외가 있으면 명시한다.

검증 규칙에는 공통 권한·범위·상태 조건과 도메인별 생성·수정·삭제·복구·공개 행동의 성공 조건을 기록한다. 입력 형식, 중복 기준, 참조 범위, 상태 전이, 사용 중지·삭제 상태의 제약을 행동별로 분리하고, 실패 결과 자체는 다음 실패 조건 단계에서 정의한다.

실패 조건에는 검증 실패 시 바뀌지 않아야 할 상태, 권한·범위·입력·중복·참조·상태 충돌별 실패 조건, 접근 불가·선택 불가·기존 표기·404 같은 시스템 결과를 기록한다. 화면 문구, HTTP 상태 코드, API 오류 형식은 이 단계에서 정하지 않는다.

상태 정의 및 전이 문서에는 상태를 가진 각 도메인, 최초 상태, 허용 전이, 전이 주체와 결과, 전이 금지 조건을 기록한다. 공통 `use_yn`·`del_yn` 같은 횡단 상태와 도메인 고유 상태를 구분하며, 하나의 행동이 여러 상태를 바꿀 때에는 상태별 책임과 순서를 명확히 한다.

## 5단계: 프론트 라우트·API 설계

라우트·API 설계는 4차 기획의 다섯 문서가 확정되고 상태·권한·실패 경계에 미결 사항이 없을 때 시작한다.

1. 공개 열람, 인증, 전역 관리, 월드 관리, 프로젝트 작성 관리로 페이지 책임을 나눈다.
2. 페이지마다 사용자, 진입 경로, 핵심 데이터, 주요 행동, 권한 필터, 주요 이동 경로를 기록한다.
3. 전역·월드·프로젝트 대시보드는 행동 중심 관리 허브로 설계하고, 간단한 관리 행동과 전문 페이지로 이어지는 작업 진입점을 제공한다.
4. 모든 확정 유스케이스를 하나 이상의 페이지와 API 영역에 연결해 상위 근거 없는 화면·기능과 하위 누락을 막는다.
5. API는 인증·관리·공개 네임스페이스를 분리하고, 네임스페이스 아래의 리소스와 상태 전이 사건은 복수형으로 작성한다.
6. 관리 API는 내부 UUID를 사용하고 공개 API는 월드·프로젝트 슬러그와 문서상 이름을 사용한다.
7. 성공과 실패 응답은 같은 키를 사용하고, 권한·입력·중복·상태·리비전·토큰 실패를 화면이 구분할 수 있는 세부 코드와 정보로 정의한다.
8. 설계 결과는 지속 제품 계약과 작업별 작성·검증 절차로 나누어 `docs/project-design/`과 `docs/work-design/`에 기록한다.

이 단계의 확정은 라우트 파일, 페이지 컴포넌트, API 핸들러, 타입, 테스트, ORM, 마이그레이션, 데이터베이스 변경의 구현 승인을 뜻하지 않는다. 옴니노드의 현재 상세 기준은 `docs/project-design/2026-09-03-omninode-route-api-design.md`를 따른다.

## 1차 기획 결정 기록 작성 방식

- 1차 기획 결정 기록은 서비스 전체에 지속되는 제품 설계 문서로 `docs/project-design/`에 작성한다.
- 문서는 도메인별 제목을 두고, 각 결정은 번호를 붙인 짧고 단정적인 문장으로 기록한다.
- `확정 결정`에는 마스터가 직접 선택하거나 명시한 내용만 기록한다. 확정한 원칙에서 바로 도출되는 사항은 파생 규칙임을 분명히 하여 기록한다.
- 기존 결정을 마스터가 정정하면 이전 문장을 남겨 모순되게 하지 않고, 현재 의도가 드러나도록 해당 기록을 수정한다.
- 구현 방식, API, 데이터베이스 구조, 화면 배치처럼 1차 기획의 범위를 벗어난 내용은 결정 기록에 넣지 않는다.
- 아직 결론이 없는 항목은 `미결 결정`으로 분리하고, 추측으로 빈칸을 채우지 않는다.
- 선택 또는 정정 직후 기록하고 `git diff --check`를 실행해 문서 형식을 확인한다.

## 사용자 스토리 기능 목록화

1. 기초 기획과 1차 기획의 확정 결정 기록만을 근거로 지원 기능을 추출한다.
2. 각 기능은 `누가`, `무엇을`, `왜`의 형태를 갖는 사용자 스토리로 작성한다.
3. 사용자 스토리는 도메인별로 묶되, 한 스토리에 서로 다른 기능을 섞지 않는다.
4. 확정된 기능은 `확정 사용자 스토리`에만 기록한다. 이 목록은 구현 순서나 구현 승인 목록이 아니다.
5. 기초 기획의 목표를 달성하는 데 필요해 보이지만 마스터가 아직 확정하지 않은 기능은 문서 하단 `추가 검토 필요 기능`에 분리한다.
6. 추가 검토 필요 기능은 확정 기능처럼 표현하지 않고, 왜 검토가 필요한지와 함께 적는다.
7. 새 결정이 생기면 사용자 스토리 목록과 1차 기획 결정 기록의 관계를 함께 확인한다.

## 사용자 스토리 작성 방식

- 확정 사용자 스토리는 `US-번호. <사용자 역할>로서 <원하는 행동>하고 싶다. <얻는 목적 또는 결과>.` 형식으로 작성한다.
- 한 스토리에는 사용자가 달성하려는 하나의 행동 또는 결과만 넣는다. 서로 독립적인 행동은 별도 스토리로 나눈다.
- API, 데이터베이스, 화면 구성, 내부 코드처럼 구현 방법을 스토리 본문에 넣지 않는다.
- 1차 기획에서 확정한 제약·예외·권한 범위는 사용자가 기대하는 결과로 풀어 쓴다.
- 근거가 없는 기능을 확정 사용자 스토리로 추가하지 않는다. 필요한 가능성이 있는 기능은 `추가 검토 필요 기능`에 후보 번호와 검토 이유를 함께 적는다.
- 상세 스토리에는 추적을 위한 `US-번호`를 부여하고, 우선순위 인덱스에서는 해당 번호를 사용한다.

## 사용자 스토리 정렬 기준

확정 사용자 스토리는 아래 우선순위 순서로 상단 인덱스에 나열한다. 상세 스토리 본문은 도메인별로 유지해 근거를 추적한다.

- **P0 — 핵심 작성 기반:** 월드 설정을 구조화해 작성·보존하는 최소 기능이다. 이 기능 없이 옴니노드를 노션의 대체 도구로 사용할 수 없다.
- **P1 — 기본 서비스 완성:** 공동 관리와 공개 열람을 포함해, 작성한 설정을 실제 서비스로 운영하기 위한 기능이다.
- **P2 — 안전한 운영과 예외 처리:** 변경·삭제·비활성화처럼 기존 데이터를 위험 없이 관리하기 위한 기능이다.

우선순위는 기능의 필요성 순서이며, 구현 승인이나 실제 개발 일정을 뜻하지 않는다.

## 유스케이스 구체화

유스케이스는 사용자가 특정 목적을 달성하기 위해 시스템과 상호작용하는 흐름을 정의한다. 기능 목록을 나열하는 것이 아니라 실제 사용 상황을 기준으로 작성한다. 사용자 스토리가 `누가, 무엇을, 왜 원하는가`를 정의한다면, 유스케이스는 그 목적을 실제로 어떤 흐름으로 달성하는가를 정의한다.

### 기본 원칙

- 하나의 유스케이스는 하나의 명확한 사용자 목적을 다룬다.
- 반드시 행위자가 누구인지 명확히 한다.
- 하나의 유스케이스는 대응하는 `US-번호`를 반드시 기록한다. 하나의 사용자 스토리에서 서로 구분되는 목적이나 흐름이 있으면 여러 유스케이스로 나눌 수 있다.
- 사용자가 무엇을 하려는지와 시스템이 어떻게 반응하는지를 함께 작성한다.
- 정상적인 기본 흐름을 먼저 정의하고, 필요한 경우 대안 흐름과 예외 상황을 추가한다.
- 화면 배치, 컴포넌트 종류, 버튼 위치 등 UI 세부 구현은 정의하지 않는다.
- API, HTTP 메서드, DB 쿼리, ORM, 프레임워크 등 기술 구현 방식은 정의하지 않는다.
- 데이터 구조를 미리 확정하지 않는다. 필요한 데이터의 의미와 변화만 식별한다.
- 사용자 스토리에 존재하지 않는 기능이나 요구사항을 임의로 추가하지 않는다.
- 유스케이스 작성 중 새로운 요구사항이나 정책 결정이 필요한 경우 임의로 결정하지 않고 `미결 사항`으로 분리한다.
- 해당 결정이 유스케이스 확정에 반드시 필요하면 마스터에게 하나의 결정 단위로 질문하고, 지금 결정할 필요가 없으면 `미결 사항`으로 분리한다.
- 동일한 행동이라도 목적이 명확히 다른 경우 별도의 유스케이스로 분리한다.
- 지나치게 작은 클릭이나 입력 단위를 각각 유스케이스로 만들지 않는다.

### 기본 구성

각 유스케이스는 필요에 따라 아래 항목을 작성한다. 모든 항목을 기계적으로 채울 필요는 없으며, 해당 유스케이스를 이해하는 데 필요한 항목만 작성한다.

- **이름:** 사용자의 목적이 드러나는 행동형 이름
- **행위자:** 해당 행동을 수행하는 사용자 또는 시스템 주체
- **목적:** 이 유스케이스를 수행하는 이유
- **사전 조건:** 유스케이스 실행 전에 충족되어야 하는 조건
- **기본 흐름:** 정상적으로 목적을 달성하는 과정
- **대안 흐름:** 정상 흐름에서 선택 가능한 다른 경로
- **예외 흐름:** 실패하거나 진행할 수 없는 상황
- **결과:** 유스케이스 완료 후 시스템 상태
- **관련 데이터:** 과정에서 조회·생성·수정·삭제되는 데이터의 개념

### 작성 수준과 연결 원칙

- 단순한 클릭이나 입력은 사용자의 목적이 아니라 UI 행동이므로 유스케이스로 작성하지 않는다.
- 유스케이스에는 시스템의 기술 처리 방법이 아니라 사용자의 행동과 그에 대한 시스템 반응을 작성한다.
- 하나의 사용자 스토리에서 여러 유스케이스가 파생될 수 있다.
- 유스케이스 단계에서는 DB 컬럼이나 테이블을 먼저 결정하지 않는다. 필요한 데이터의 의미와 상태 변화만 기록한다.
- 유스케이스가 확정된 이후, 각 흐름에서 어떤 데이터가 이동하거나 변경되는지는 데이터 플로우 단계에서 구체화한다.
- 유스케이스 작성이 끝나면 각 `UC-번호`가 하나 이상의 확정 `US-번호`와 연결되는지 확인하고, 상위 근거가 없는 유스케이스가 생기지 않게 한다.

### 검토 기준

- 사용자의 목적이 명확한가?
- 사용자 스토리와 연결되는가?
- 정상적인 시작과 종료가 존재하는가?
- 시스템의 반응이 정의되어 있는가?
- 중요한 대안·예외 상황이 빠지지 않았는가?
- 행위자, 필요한 사전 조건, 완료 뒤 사용자·시스템 상태 변화가 이해 가능한가?
- UI 설계나 기술 구현이 섞이지 않았는가?
- 아직 결정되지 않은 정책을 임의로 가정하지 않았는가?
- 이후 데이터 플로우를 작성할 수 있을 정도로 행동 흐름이 명확한가?

## 유스케이스 데이터 플로우 구체화

유스케이스가 확정된 다음에는, 각 유스케이스가 어떤 데이터를 읽고 만들고 바꾸고 보존하는지 구체화한다. 이 작업은 데이터 스키마를 구상하기 위한 근거를 만든다.

- 유스케이스 하나 또는 강하게 연결된 유스케이스 묶음마다 데이터 플로우를 작성하고, 대응하는 `UC-번호`와 `US-번호`를 적는다.
- 데이터 플로우는 유스케이스에서 확정된 사용자 행동과 시스템 반응만을 근거로 작성하며, 새 사용자 행동이나 제품 정책을 임의로 추가하지 않는다.
- 각 플로우는 `주체와 시작 조건`, `읽기·검증`, `생성·변경·보존 데이터`, `결과와 후속 상태` 순으로 작성한다.
- 현재 상태와 리비전·공개본·감사 이력처럼 과거 상태를 보존하는 데이터를 구분한다.
- 월드·프로젝트 범위, 권한, 공개 여부, 삭제 상태처럼 데이터 접근과 처리 결과를 바꾸는 조건을 명시한다.
- 하나의 유스케이스에서 기본·대안·예외 흐름에 따라 데이터 처리가 실질적으로 달라지면 그 차이를 데이터 플로우에 반영한다.
- 여러 유스케이스가 같은 데이터 처리 규칙을 공유하더라도 어느 `UC-번호`에서 쓰는 흐름인지 추적할 수 있게 한다.
- 데이터 플로우 문서에는 테이블, 컬럼, ORM, API 같은 구현 구조를 넣지 않는다. 이 문서를 근거로 하는 데이터 스키마 구상은 별도 작업이다.

## 단계 간 추적성 점검

2차·3차 보강에서 작성되는 주요 항목은 가능한 한 다음 관계를 따라 근거를 추적할 수 있어야 한다.

`1차 기획 확정 결정 → US-번호 → UC-번호 → 데이터 플로우 → 데이터 스키마`

- 유스케이스는 대응하는 확정 사용자 스토리를 가져야 한다.
- 데이터 플로우는 대응하는 유스케이스를 가져야 한다.
- 데이터 스키마의 주요 엔티티·상태·관계·제약은 이를 요구하는 데이터 플로우를 추적할 수 있어야 한다.
- 하위 단계에서 상위 근거를 찾을 수 없는 기능·흐름·데이터 구조가 발견되면, 에이전트가 임의로 추가한 내용인지 먼저 확인한다.
- 상위 단계에서 확정된 내용이 하위 단계에 반영되지 않았다면 누락 여부를 확인한다.
- 하위 단계에서 새로운 제품 정책이 필요하다는 사실이 발견되면 상위 기록을 조용히 수정하거나 추정하지 않고, 필요한 결정 단계로 돌아가 마스터와 확정한다.

## 데이터 스키마 구상

데이터 플로우가 확정되면, 이를 근거로 데이터의 식별·범위·상태·이력·연결을 테이블과 컬럼 수준으로 구상한다. 이 단계는 데이터베이스 변경을 실행하는 단계가 아니다.

- 스키마 초안을 작성한 뒤, 3차 보강을 확정하기 전에 테이블 간 참조·범위·삭제 처리·제약을 점검한다. 점검에서 발견한 모호성은 마스터와 결정한 뒤 스키마 구상에 반영한다.
- 데이터 플로우의 데이터 묶음마다 엔티티, 각 엔티티의 책임, 다른 엔티티와의 연결, 보존해야 할 상태와 제약을 먼저 정리한다.
- 한 번에 하나의 결정 단위만 다루고, 이미 확정된 제품 규칙의 직접적인 데이터 구조상 결과는 재질문하지 않는다.
- 물리 테이블명과 컬럼명은 기본적으로 `snake_case`를 사용한다.
- 물리 테이블명은 복수형으로 통일한다.
- 모든 테이블의 기본 키는 UUID v7을 사용하는 `id` 컬럼으로 통일한다. 다른 테이블의 참조 컬럼도 대상 테이블 이름을 따른 `*_id` 형식의 UUID v7을 사용한다.
- 새 DB 식별자는 `G:\내 드라이브\공통표준용어`의 `공통표준용어 운영 지침.md`, 공통표준단어, 커스텀단어, 단어별칭, `DB 이름 짓기` 시트를 함께 확인해 표준 약어와 조합 결과를 적용한다. 직접 일치와 별칭의 우선순위는 운영 지침을 따른다.
- 공통표준용어에 직접 일치하는 단어·대표어·별칭·원자어 또는 `DB 이름 짓기` 조합 결과가 없는 단어는 임의의 영문명·약어·물리 식별자로 만들지 않는다.
- 이 경우 기존 용어와의 충돌 여부를 확인한 뒤, 해당 단어를 공통표준용어에 추가할 필요가 있는지 마스터와 먼저 논의한다.
- 마스터의 결정 없이 공통표준용어 사전에 새 단어·약어를 추가하거나, 그 단어를 사용하는 새 물리 식별자를 확정하지 않는다.
- 모든 테이블에는 공통 상태·감사 컬럼을 둔다. `use_yn`, `del_yn`, `creatr_id`, `crt_dt`, `mdfr_id`, `mdfcn_dt`, `dltr_id`, `del_dt`이며, `use_yn`과 `del_yn`은 길이 1의 문자열 `Y` 또는 `N`만 허용한다. 새 행은 `use_yn`을 `Y`, `del_yn`을 `N`으로 시작한다. 사용 중지와 소프트 딜리트는 별개 상태이며, 삭제 처리와 복구는 `use_yn`을 바꾸지 않는다. 날짜 컬럼은 `yyyy-MM-dd HH:mm:ss.sss` 정밀도로 저장한다. 아직 발생하지 않은 수정·삭제 작업의 컬럼 값은 비워 둔다.
- 데이터 스키마 문서에는 테이블별 컬럼·형식·제약을 표로 작성한다. 마스터에게는 기능·정책·흐름처럼 제품 판단이 필요한 내용만 질문하고, 확정된 공통 컬럼과 그 기술적 파생값은 질문 없이 반영한다.
- 데이터 스키마 문서에는 확정된 테이블·컬럼·키·제약·상태값과 그 근거를 기록한다. ORM 코드, 마이그레이션, DDL, 데이터베이스 변경은 별도 구현 승인 뒤에만 다룬다.
