# 옴니노드 유스케이스 후행 작성 정합성 점검

> 분류: 작업 설계
>
> 점검 사유: 유스케이스가 사용자 스토리와 데이터 플로우 뒤에 작성되었으므로, 1차 기획부터 스키마까지의 추적 관계와 확정 정책의 불일치를 점검한다.
>
> 점검 대상: `2026-08-29-omninode-requirements-decisions.md`, `2026-08-29-omninode-user-stories.md`, `2026-08-30-omninode-use-cases.md`, `2026-08-29-omninode-user-story-data-flow.md`, `2026-08-29-omninode-data-schema.md`
>
> 범위: 사용자 목적·행위자·정상 및 예외 흐름·상태 변화·권한·리비전·공개·삭제·주소 규칙의 일치 여부를 점검한다. 화면, API, ORM, DDL, 마이그레이션은 포함하지 않는다.

## 점검 기준

1. 1차 기획의 확정 정책은 사용자 스토리·유스케이스·데이터 플로우·스키마에서 서로 모순되지 않아야 한다.
2. 사용자 스토리는 하나 이상의 유스케이스 또는 데이터 플로우 묶음에서 추적할 수 있어야 한다.
3. 유스케이스는 화면·API·테이블 구현을 미리 결정하지 않고, 사용자 행동과 시스템 반응만 다뤄야 한다.
4. 데이터 플로우와 스키마는 유스케이스에서 식별한 상태 변화와 권한 제한을 빠뜨리지 않아야 한다.
5. 이미 확정된 정책의 직접적인 결과는 별도 기획 논의 없이 문서에 일관되게 반영한다.

## 점검 결과

| 점검 영역 | 결과 | 확인·반영 내용 |
| --- | --- | --- |
| 사용자 스토리 → 유스케이스 | 통과 | 계정·권한, 월드·프로젝트, 카테고리·템플릿, 문서·위키링크·태그, 관계, 공개 열람의 확정 사용자 스토리를 UC-01부터 UC-25까지 연결했다. |
| 유스케이스 → 데이터 플로우 | 보완 완료 | 공개 주소 사용자 스토리 US-71이 유스케이스 문서의 DF-09 연결표에서 누락돼 있어 추가했다. |
| 문서 이름 변경 흐름 | 보완 완료 | 일반 문서 수정 흐름에서 이름을 바꿀 수 있다고 적힌 표현을 제거했다. 이름 변경은 문서 관리 흐름에서만 수행하고, 그 결과를 새 문서 리비전으로 보존하도록 UC-19와 DF-05·DF-06을 정정했다. |
| 리비전·템플릿 반영 | 통과 | 저장 시 새 문서 리비전 생성, 되돌리기 자체의 무리비전, 저장 시 최신 템플릿 구조 적용, 공개본과 현재 문서의 분리를 동일하게 유지한다. |
| 태그·관계의 독립성 | 통과 | 문서 저장에는 태그 상태를 보존하되 관계 인스턴스의 현재 상태는 문서 리비전과 분리한다. 삭제 태그·비공개 문서·삭제 문서의 뷰어 표기도 일치한다. |
| 역할·세부 허가 | 보완 완료 | 부관리자에게 월드 관리·부관리자 초대·관계 관리·태그 목록 관리 허가를 줄 수 없다는 정책이 24개 허가 컬럼 설명에 명시되지 않아, 실제 허가와 초대 허가 스냅샷 모두에 `N` 고정 제약을 추가했다. 문서 허가에 포함되는 태그 연결·새 태그 추가와 태그 목록 관리 허가를 분리했다. |
| 삭제·복구·탈퇴 | 통과 | 일반 데이터의 소프트 딜리트, 상위 범위 삭제 시 하위 상태 보존, 계정 탈퇴의 7일 내려받기와 예외적 완전 삭제, 소유권 승계가 각 문서에서 같은 결과를 가리킨다. |
| 공개 주소·문서 이름 | 통과 | 월드·프로젝트 슬러그의 직접 입력·범위별 중복·대소문자 비구분과, 문서 이름의 최대 3개 경로 구간·이전 주소 404 정책이 유스케이스·데이터 플로우·스키마에 반영돼 있다. |

## 비즈니스·기획 논의 필요 사항

- 없음. 발견한 항목은 모두 이미 확정된 정책을 문서에 빠짐없이 맞추는 수준이어서, 별도 선택을 요청하지 않고 정정했다.

## 점검 결론

- 유스케이스가 후행 작성된 데서 생긴 사용자 목적·정책·추적 관계의 불일치는 정정했다.
- 현재 1차 기획, 사용자 스토리, 유스케이스, 데이터 플로우, 데이터 스키마는 프론트 라우트와 API 엔드포인트 설계로 넘어갈 수 있는 상태다.
