# 옴니노드 라우트·API 설계 문서화

> 분류: 작업 설계
>
> 근거: 마스터가 확정한 프론트 라우트·API 설계안
>
> 대상: `docs/project-design/2026-09-03-omninode-route-api-design.md`, 프로젝트·사용자 `AGENTS.md`
>
> 구현 경계: 설계 문서와 지속 작업 지침만 갱신한다. `app/pages/`, `server/`, API 타입, 테스트, ORM, 마이그레이션, 데이터베이스는 변경하지 않는다.

## 작업 목적

1. 확정된 33개 페이지 역할을 이후 화면 설계와 구현에서 다시 해석하지 않도록 기록한다.
2. 25개 유스케이스를 페이지와 API에 연결해 기능 누락을 방지한다.
3. API 네임스페이스, 복수형 리소스, 식별자, 상태 전이, 응답·오류 계약을 공통 기준으로 고정한다.
4. 전역·월드·프로젝트 대시보드를 행동 중심 관리 허브로 사용하는 원칙을 지속 지침에 반영한다.

## 문서 작성 순서

1. 공개·인증·전역·월드·프로젝트 관리 범위로 페이지를 나눈다.
2. 각 페이지에 사용자, 진입 경로, 핵심 데이터, 주요 행동, 권한 필터, 주요 이동 경로를 기록한다.
3. 전역·월드·프로젝트 대시보드가 직접 처리하는 행동과 전문 페이지로 넘기는 행동을 구분한다.
4. 인증, 전역 관리, 월드·프로젝트, 카테고리·템플릿, 문서·태그, 관계, 공개 열람 순서로 API 엔드포인트를 기록한다.
5. 모든 API 리소스명과 상태 전이 사건명을 복수형으로 맞춘다.
6. 성공·실패 공통 응답, 페이지 목록, 충돌·권한·토큰·검증 오류 규칙을 기록한다.
7. UC-01부터 UC-25까지 대응 페이지와 API 영역을 연결한다.
8. 지속 적용할 규칙만 프로젝트와 사용자 `AGENTS.md`에 요약한다.

## 추적성 점검 기준

| 점검 항목 | 통과 조건 |
| --- | --- |
| 페이지 수 | P-01부터 P-33까지 중복·누락 없이 존재한다. |
| 페이지 설명 | 모든 페이지에 사용자, 경로, 데이터, 행동, 권한 필터, 이동 경로가 있다. |
| 유스케이스 | UC-01부터 UC-25까지 각각 하나 이상의 페이지와 API 영역에 연결된다. |
| API 네임스페이스 | 모든 엔드포인트가 `/api/v1/auth`, `/api/v1/management`, `/api/v1/public` 중 하나에 속한다. |
| 복수형 리소스 | `sessions`, `worlds`, `documents`, `restorations`처럼 경로의 리소스와 사건 이름이 복수형이다. `auth`, `management`, `public`은 네임스페이스로 예외 처리한다. |
| 관리·공개 식별자 | 관리 API는 UUID를, 공개 API는 월드·프로젝트 슬러그와 문서상 이름을 사용한다. |
| 응답 동형성 | 성공과 실패 모두 `data`, `error`, `code`, `message`, `details`를 포함하며 `details`는 생략하지 않는다. |
| 전송 결과 | 모든 API 성공·실패 응답은 HTTP 200이며 클라이언트는 자동 재시도하지 않는다. |
| 대시보드 | 전역·월드·프로젝트 대시보드가 상태·할 일·간단한 관리 행동과 전문 페이지 이동을 가진다. |
| 제외 범위 | 통합 휴지통, 일반 회원가입, 토론, 사용자용 백업·내보내기 페이지·API를 추가하지 않는다. |
| 구현 경계 | 라우트 파일, API 코드, 타입, 테스트, ORM, DB 변경이 섞이지 않는다. |

## 설계 수용 시나리오

1. 미인증 사용자가 관리 URL에 접근하면 원래 경로를 보존해 로그인으로 이동할 수 있다.
2. 임시 비밀번호 계정은 비밀번호 변경 전까지 일반 관리 페이지와 API를 사용할 수 없다.
3. 기존 계정 초대와 신규 계정 초대가 같은 초대 페이지에서 각자의 인증 흐름으로 이어진다.
4. 운영자·관리자·부관리자는 같은 대시보드 경로에서도 현재 범위와 허가에 맞는 카드와 행동만 받는다.
5. 프로젝트 관리 권한만 있는 부관리자도 프로젝트 대시보드에서 프로젝트 자체를 관리할 수 있다.
6. 삭제된 동명 항목을 발견하면 복구와 별도 새 생성 중 하나를 선택할 수 있다.
7. 카테고리 이동 전 영향을 확인하고, 이동 뒤 문서·관계의 점검과 공개 제한을 추적할 수 있다.
8. 템플릿·문서 저장 충돌은 `baseRevisionId`로 감지하며 기존 저장본을 덮어쓰지 않는다.
9. 문서 저장, 과거 리비전 적용, 문서 이동, 공개본 지정은 서로 다른 결과와 엔드포인트를 가진다.
10. 관계 유형 비활성화로 종료된 관계와 직접 삭제한 관계는 복구 경로를 갖지 않는다.
11. 공개 화면은 선택된 공개 리비전만 사용하고 비공개·삭제 연결의 내부 식별자와 이름을 숨긴다.
12. 공개 문서 이름 변경 전 주소는 리다이렉트 없이 404가 된다.
13. API 처리 결과는 모두 HTTP 200 응답 본문의 공통 키로 판별하며 실패한 요청을 자동 재시도하지 않는다.

## 검증 방법

1. Markdown 표의 P-번호와 UC-번호를 추출해 번호 연속성과 개수를 확인한다.
2. API 경로를 추출해 허용 네임스페이스와 단수형 금지 목록을 확인한다.
3. `rg`로 제외 대상 라우트·API가 확정 목록에 들어가지 않았는지 확인한다.
4. `git diff --check`로 후행 공백과 문서 형식 오류를 확인한다.
5. `git diff --stat`과 `git status --short`로 코드·DB 파일이 변경되지 않았는지 확인한다.

## 기준선 기록

- 문서 작업 전 `pnpm test`는 12개 테스트 파일 중 6개 파일이 실패했다.
- 기존 실패는 누락된 API composable·query fetcher·query key 파일, 기본 레이아웃의 `storeToRefs` 테스트 환경, `UiPanel`의 `rounded-1`과 기존 테스트 기대값 불일치다.
- 이번 문서 작업은 해당 실패를 수정하지 않는다. 완료 판단은 문서 대상 검증과 변경 범위 검증으로 분리한다.

## 완료 기준

- 제품 설계 문서에 P-01~P-33과 UC-01~UC-25의 추적 관계가 기록돼 있다.
- API 복수형 명명, 세 네임스페이스, 관리·공개 식별자 구분과 상태 전이 엔드포인트가 기록돼 있다.
- 성공·실패 동형 응답과 항상 존재하는 `details`가 기록돼 있다.
- 모든 API 응답의 HTTP 200 원칙과 자동 재시도 금지 원칙이 기록돼 있다.
- 행동 중심 대시보드 원칙과 설계·구현 경계가 프로젝트·사용자 지침에 반영돼 있다.
- 문서 형식과 변경 범위 검증이 통과한다.
