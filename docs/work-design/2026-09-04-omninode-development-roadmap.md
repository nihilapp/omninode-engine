# 옴니노드 개발 로드맵

> 분류: 작업 설계
>
> 상태: 2026-09-04 정식 채택
>
> 근거: 제품 설계 33개 테이블, 33개 페이지 역할, 25개 유스케이스와 라우트·API 설계

## 목적

제품 설계와 실제 구현 사이의 간격을 단계적으로 줄이고, 각 단계에서 사용자 흐름을 끝까지 검증할 수 있는 개발 순서를 정한다. 데이터·인증·권한 기반을 먼저 세운 뒤에는 도메인별 API와 페이지를 함께 완성한다.

이 문서는 장기 개발 순서의 기준이다. 실제 완료 상태는 `omninode-progress.md`에서 관리하고, 각 단계의 상세 설계와 구현 계획은 해당 단계에 진입할 때 별도로 작성한다.

## 채택한 개발 방식

옴니노드는 **기반 구축 후 기능별 세로 개발 방식**을 사용한다.

1. 데이터, 인증, 권한은 모든 관리 기능이 공유하므로 먼저 구축한다.
2. 이후에는 월드·프로젝트, 카테고리·템플릿, 문서처럼 사용자 목적을 기준으로 API와 페이지를 함께 구현한다.
3. 전체 API를 먼저 만든 뒤 페이지를 한꺼번에 붙이거나, 데이터 계약 없이 화면부터 대량으로 만드는 방식은 사용하지 않는다.
4. 대시보드는 관련 기능이 구현될 때마다 행동과 집계를 단계적으로 연결하고 마지막 검증 단계에서 전체 구성을 완성한다.

## 전체 순서

```text
제품 스키마 구현 설계
→ 데이터베이스 기반
→ 인증
→ 권한
→ 월드·프로젝트
→ 초대·소속
→ 카테고리·템플릿
→ 문서·리비전
→ 관계
→ 공개·탐색
→ 탈퇴·운영 예외
→ 전체 인수 검증
```

## 단계별 개발 루트

### M01. 제품 스키마 구현 설계

- 진행 항목: `DATA-01`
- 목표: 확정된 33개 테이블을 실제 Prisma·PostgreSQL 구현 단위로 변환할 기준을 확정한다.
- 주요 작업:
  - 세션 저장 방식과 강제 로그아웃·탈퇴 즉시 차단 방식을 결정한다.
  - Prisma 선언 제약과 별도 마이그레이션 SQL 제약을 구분한다.
  - UUID v7, 공통 감사 컬럼, 순환 참조와 테이블 생성 순서를 설계한다.
  - 최초 운영자 생성과 시스템 기본 데이터 입력 방식을 설계한다.
  - 스키마·마이그레이션·제약 통합 테스트 범위를 정한다.
- 완료 기준: 스키마 구현자가 추가 판단 없이 모델, 마이그레이션과 검증을 작성할 수 있는 설계와 계획이 승인되어 있다.

M01에서 먼저 다룰 기술 결정은 아래와 같다.

1. API는 `HttpOnly` 세션 쿠키를 사용하지만 현재 제품 스키마에는 세션 저장 구조가 없다. 강제 로그아웃과 탈퇴 즉시 차단을 지원하기 위해 DB 저장형 불투명 세션을 우선 검토한다.
2. 기본 관계 유형 936개와 기본 카테고리·템플릿의 실제 초기 데이터 출처와 적재 방식을 정한다.
3. 소프트 삭제 제외 고유 제약, 범위 정합성, 최대 깊이처럼 Prisma만으로 보장하기 어려운 규칙의 DB 구현 방식을 정한다.
4. 최초 운영자 한 건만 `creatr_id`를 비울 수 있는 초기화 절차를 정한다.

위 항목의 검토 우선순위는 확정했지만, 개별 구현 방식은 M01 설계에서 한 결정 단위씩 확정한다.

### M02. 데이터베이스 기반 구현

- 진행 항목: `DATA-02`
- 목표: 빈 데이터베이스에서 옴니노드의 제품 데이터 구조를 재현할 수 있게 한다.
- 주요 작업:
  - 임시 `User` 모델을 제거하고 제품 모델을 구현한다.
  - 최초 마이그레이션과 DB 전용 제약·인덱스를 작성한다.
  - 최초 운영자 생성 절차와 시스템 기본 데이터 적재를 구현한다.
  - 참조, 범위, 삭제, 복구와 초기화 과정을 통합 테스트한다.
- 완료 기준: 신규 데이터베이스에 동일한 구조와 초기 데이터를 반복 적용할 수 있고 모든 스키마 검증이 통과한다.

### M03. 인증 기반

- 진행 항목: `AUTH-01`
- 목표: 실제 관리자 계정으로 안전하게 로그인하고 인증 상태를 관리한다.
- 주요 작업:
  - 로그인, 현재 세션 확인과 로그아웃을 구현한다.
  - 임시 비밀번호 변경과 변경 전 관리 접근 제한을 구현한다.
  - 비밀번호 재설정 요청·확인·완료를 구현한다.
  - 미인증 이동의 `returnTo`와 인증 미들웨어를 구현한다.
  - `/signin`, `/password/change`, `/password/forgot`, `/password/reset/[token]`을 함께 구현한다.
- 완료 기준: 인증 API와 페이지가 HTTP 200 공통 응답, 명시적 사용자 재요청, 세션 보안 규칙을 함께 만족한다.

### M04. 권한 판정 기반

- 진행 항목: `PERM-01`
- 목표: 모든 관리 요청이 같은 역할·범위·세부 허가 규칙을 사용하게 한다.
- 주요 작업:
  - 운영자·관리자·부관리자 역할과 전역·월드·프로젝트 범위를 판정한다.
  - 가장 좁은 범위의 허가를 우선 적용하고 24개 허가를 실제 행동에 연결한다.
  - 권한 부족과 관리 범위 밖 결과를 구분한다.
  - 서버 API, 직접 URL과 메뉴 노출이 같은 판정을 사용하게 한다.
- 완료 기준: 역할별 API·직접 URL·메뉴 접근 결과가 권한 매트릭스와 일치한다.

### M05. 월드·프로젝트 관리

- 진행 항목: `MGMT-01`, `PAGE-01`
- 목표: 관리자가 로그인해 월드와 프로젝트를 만들고 관리할 수 있게 한다.
- 주요 작업:
  - 계정, 월드와 프로젝트의 조회·생성·수정·삭제·복구를 구현한다.
  - 전역·월드·프로젝트 관리 진입 화면과 기본 대시보드를 구현한다.
  - 프로젝트 생성 시 시스템 기본 카테고리·템플릿 참조를 초기화한다.
- 대응 유스케이스: `UC-01`, `UC-06`, `UC-07`, `UC-08`
- 완료 기준: 관리자가 월드와 프로젝트를 생성하고 삭제·복구까지 수행할 수 있다.

### M06. 초대·소속·권한 위임

- 진행 항목: `AUTH-01`, `PERM-01`, `MGMT-01`, `PAGE-01`
- 목표: 월드 관리자가 부관리자를 초대하고 범위와 권한을 관리할 수 있게 한다.
- 주요 작업:
  - 신규·기존 계정 초대, 확인, 수락, 취소와 재발송을 구현한다.
  - 월드 소속, 프로젝트 범위와 세부 허가 변경·해제를 구현한다.
  - 초대·소속·권한 변경 감사 이력을 구현한다.
- 대응 유스케이스: `UC-02`, `UC-03`, `UC-25`
- 완료 기준: 초대부터 권한 적용과 감사 이력 확인까지 하나의 흐름으로 검증된다.

### M07. 카테고리·템플릿

- 진행 항목: `MGMT-01`, `PAGE-01`
- 목표: 문서를 작성하기 위한 프로젝트별 분류와 문서 구조를 구성한다.
- 주요 작업:
  - 카테고리 트리와 프로젝트별 사용 상태를 구현한다.
  - 템플릿, 영속 섹션과 템플릿 리비전을 구현한다.
  - 대분류와 템플릿 연결, 활성화·비활성화·복구를 구현한다.
  - 카테고리 이동 미리보기, 영향 표시와 점검 완료를 구현한다.
- 대응 유스케이스: `UC-09`~`UC-13`
- 완료 기준: 문서 작성 가능한 카테고리와 템플릿 구성을 만들고 변경 영향을 검증할 수 있다.

  - 태그 자동 생성·연결과 위키링크·역링크를 구현한다.

- 진행 항목: `QA-01`, `PAGE-01`
- 목표: 개별 기능을 제품 전체 흐름으로 연결하고 첫 버전 완료 여부를 판정한다.
- 주요 작업:

## 단계 운영 규칙

1. 각 단계는 별도의 설계 승인, 구현 계획, 구현과 검증 단위로 진행한다.
2. 단계가 한 번에 구현하기 크면 사용자 가치가 독립적으로 검증되는 하위 작업으로 나누되 전체 순서는 유지한다.
3. M03 이후에는 해당 도메인의 API와 페이지를 함께 구현한다.
4. 모든 API는 복수형 리소스, HTTP 200 공통 응답과 자동 재시도 금지 원칙을 유지한다.
5. 구현 산출물과 해당 범위의 테스트가 모두 확인된 경우에만 개발 현황을 완료로 변경한다.
6. 현재 진행 단계와 실제 완료 여부는 `omninode-progress.md`를 단일 기준으로 사용한다.
